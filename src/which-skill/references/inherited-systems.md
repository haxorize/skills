# Inherited systems: meeting, and leaving, a system you did not write

An **inherited system** is one the user did not write and now has to work: arrived at, ported, replaced, or handed over. Four routes record one, and this file is the tie-break between them.

Open this only when an ask concerns an inherited system — arriving at one, porting or replacing one, or an owner leaving one — and two of the four routes both plausibly fit.

- **`/onboard-repo`** — wire a repo for the suite in one sitting: the `Issue tracker:` and `Landing:` blocks the publishers and `committing` read, the `## Registry` block `upgrade-deps` reads, the loop commands, the `## Convention skills` roles, and the seed files (`DOMAIN.md`, `docs/solutions/`) — written only where nothing exists, plus the printed hook snippet. Optional: every skill degrades to asking when a block is missing.
- **`/onboard-me`** — a knowledge-transfer session over a repo you don't know: evidence-tagged findings, a KT map of what is still dark, one rung per turn, and each topic worth going deeper on handed to `/teach-me`. Writes nothing of its own, and the map lives in your Learning workspace, not the repo. Where the repo has no product description it offers one; saying yes lets `product-description` write a `docs/product-description/` directory.
- **`/rebuild-contract`** — the pre-rewrite contract for a system about to be ported or replaced: every observer at its declared boundary named with a fidelity per surface, then everything they can see written as rules a reimplementer builds from without opening the source, with the audit trail beside it under `docs/rebuild-contract/`. Reads the repo and writes only that folder, after asking. One of four records of the same inherited system, and this one fixes what must survive for whoever rebuilds it — `/onboard-me` maps the inside for the person learning it, `product-description` records the outside for a person, and `/offboard-engineer` records what leaves with a person — it declares `product-description` and calls it with `--seed` where the repo has none.
- **`/offboard-engineer`** — evidence-led knowledge capture from an engineer who is leaving: the repo is scanned for what only they can answer, ranked by how exclusively theirs and how badly the loss hurts, then one area per turn is put to them with your reading offered first — recognition, never recall — and the offboarding record — its risk register, the tagged capture, and the successor document together — lands under `docs/offboarding/`, what nobody knows first. Runs *with* the departing person, never at them, and has no unattended run — without them the same scan yields an agenda, which says so. The fourth record of one inherited system: what leaves with a person. Nothing is wired to `/onboard-me` — a successor can read the record's `[unknown]`s into that session themselves, but it takes no offboarding record as input. The register items they will answer in writing after the session go to `/ask-for-me`.

The first two are different jobs on the same first day: **`/onboard-repo`** wires the *repo* for the suite and writes config blocks into it; **`/onboard-me`** teaches the *person* the repo and writes nothing into it. Neither needs the other. The last two are the other end — a system about to be rewritten, and a person about to leave — and each writes one folder into the repo after asking.
