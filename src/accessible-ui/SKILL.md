# Accessible UI

A **success criterion** is one numbered WCAG 2.2 requirement at level A, AA, or AAA; the number and name of every A and AA criterion, with its level, is in [references/criteria.md](references/criteria.md), and a real 2.2 number absent from that list is AAA. A criterion is **touched** by a change when the change creates, alters, or removes something the criterion governs: a new button touches 2.1.1 Keyboard and 4.1.2 Name, Role, Value; a color tweak touches 1.4.3 Contrast and 1.4.11 Non-text Contrast; a CSS comment edit or a variable rename touches nothing. A criterion is **exercised** when a run was made against it. **Evidence** is a run — a keyboard walk, a screen-reader pass, a scan, a contrast measurement, a grayscale or color-vision render, a capture under an emulated preference, an accessibility-tree inspection, a text-spacing override — named by what ran and what it found, or, for a Flagged line only, a read that names the line and the criterion it fails; a belief about what the markup should do is not evidence. The **ledger** is the closed list, one line per touched criterion, in which each ends in exactly one of five states and none is silent: **Verified** (a run confirmed it), **Flagged** (a run or a read found a likely failure), **Human-required** (only a person using the assistive technology can settle it), **Not exercised** (touched, and no run was made), **N/A** (touched, and the criterion's condition does not arise in this change). The first three are the **grades**, the states evidence can support; when two runs support different grades, Flagged wins over Human-required, and Human-required wins over Verified; and where a criterion's states were only partly reached — a dialog whose open state was walked and whose error state was not — the line is **Not exercised**, never Verified on the strength of the states that were.

The test every rule serves: a person who cannot see the pointer, cannot use one, or hears the page instead of seeing it can **reach, understand, operate, and leave** every control the change touches, and the change's author has said exactly what they checked.

## Building

Every control carries four things the default output skips when nobody asks, and the contracts for the widgets the models skip most are in [references/patterns.md](references/patterns.md).

- **Reach for the most proven implementation first.** An accessible component this codebase already has, then the project's component library, then a native element, then a native element plus the minimum ARIA, and a custom widget only with its full keyboard, focus, and state behavior built end to end; on a native platform that fourth rung is reached by declaring the standard control as the custom view's accessibility representation rather than assembling the traits by hand. ARIA that restates what the native element or the library primitive already exposes (`aria-required` on a `required` input, `role="button"` on a `<button>`, a `tabindex` on a headless-library menu item) is noise, ARIA that contradicts it is a bug, and ARIA the element cannot carry — an `aria-label` on a `<div>` with no role — is neither: it is nothing. A name resting on `title` is not ARIA and fails a different way: it is the last resort of the name computation, spoken by most desktop screen readers and reaching neither touch nor most mobile ones, so a tree read shows a name the people likeliest to need it never get.
- **Name, role, state, in the accessibility tree — not in the pixels.** A chip that toggles carries `aria-pressed`; a tab carries `aria-selected`; an expander carries `aria-expanded`; a disabled control is `disabled` or `aria-disabled`, not greyed by class alone — `aria-disabled` when the reason it is off is the message the person has to reach, or when the control is only momentarily inert and native `disabled` would drop the waiting person's focus to the body; native `disabled` when the control is inert for the life of the view and there is nothing to explain. The visible look and the exposed state change together or the control lies to one audience.
- **A label is a label.** `placeholder` is a hint that vanishes on the first keystroke; a `<label for>`, `aria-label`, or `aria-labelledby` is the name. Every field, search box, and icon-only button has one, and the visible text of a label is contained in its accessible name, so voice control can say it — and names are distinct on a screen (a card's "Edit" carries the card's name), so voice control can say which.
- **The keyboard reaches what the pointer reaches, in the order the eye reads.** Hover-only reveals, drag-only reorders, and swipe-only dismissals each have a keyboard path; the tab order follows the DOM, and the DOM follows the visual order — a `tabindex` above zero is a bug. A composite control is one stop, its label, hint, and status glyph properties of that stop's name, value, and description rather than stops of their own; an interactive part inside it (a clear button, a chip's close) is its own stop, and a live region is never a stop at all.
- **Focus is never lost.** Opening a dialog or drawer moves focus into it, traps Tab inside (a focus trap), makes the rest of the page `inert` (`aria-hidden` alone leaves it focusable), and on close returns focus to the control that opened it; removing a focused element moves focus to the nearest remaining sibling or to the container first; a route change puts focus on the new heading or main and sets `<title>` to the new screen's name — the title is what the history entry and the tab carry, and the focus move is what gets announced, which is why the rule is both and not either.
- **Focus is visible.** Every focusable element shows a focus indicator with 3:1 contrast against what is behind it, in every theme; `outline: none` without a replacement is a failure, `:focus-visible` is the hook, and a `box-shadow` ring vanishes under forced colors, so it is paired with a transparent `outline` that the forced palette repaints.
- **Status is announced by a region that already exists.** A live region (`aria-live`, `role="status"`, `role="alert"`) is rendered empty before it is needed and its text set later; injecting the region with its text in one render announces nothing in most screen readers. Announce the outcome ("3 results"), not the mechanics, and never the same text twice for one event; a change either moves focus or announces, never both.
- **Meaning is not carried by color, position, or shape alone.** An error state has an icon or text beside the red; a required field has more than an asterisk color; a chart has a text alternative that states what the chart shows, and a chart whose values a reader would quote has a table that holds them. Forced colors repaints the author's palette, so a state carried only by a background fill flattens away and an icon drawn as a CSS background vanishes — the cue is a border, a glyph, or an inline `<svg>` taking `currentColor`.
- **Motion and timing respect the person.** All non-essential motion gates on the person's reduced-motion setting, read where the motion is driven — the CSS query for CSS, `matchMedia` re-read on change for script-, canvas-, and library-driven motion, the platform's environment value on native — and the gate is scoped to that non-essential motion, so stopping it outright is a compliant answer while a page-wide `animation: none` also freezes the progress indicator whose movement is essential; where the motion was carrying meaning, a fade or a shorter transition keeps it; nothing flashes more than three times a second; auto-advancing content can be paused; a timeout can be extended; a toast that carries an action never dismisses itself.
- **Targets and pointers.** A target is at least 24 by 24 CSS pixels (2.5.8), or a 24-pixel circle centered on it overlaps no other target; a drag has a single-pointer alternative; a down-event never completes an action on its own.
- **A binding action is reversible before it binds.** A submission that deletes data, commits money, or binds the person legally is reversible, confirmed, or reviewable before it commits (3.3.4 Error Prevention), the confirmation being where the destructive action becomes the primary control.
- **Text is text.** Headings are heading elements in order; lists are list elements; a table of data is a `<table>` with header cells; text in images is avoided; the shell carries a skip link to the main content. The page declares its language (3.1.1), and a block written in another one (3.1.2) — the language-assistance notice a payer must carry verbatim inside an English letter — declares its own, and its `dir` where the script runs the other way, so the block is spoken in that language's voice by the reader who needs it most; what the block says is `health-literacy`'s.
- **Text scales.** At 200% zoom no text is clipped or lost, at 320 CSS pixels wide nothing needs two-dimensional scrolling, and the viewport meta never sets `user-scalable=no` or `maximum-scale=1`, which makes that zoom impossible rather than merely broken. User-applied text spacing — line height 1.5, paragraph 2×, letter 0.12em, word 0.16em — clips nothing, and the root font size is not locked in pixels, so the browser's own text-size setting still reaches the page. On native, text uses the platform's scaling styles (a system text style, or a custom font declared relative to one) with the container's paddings and icon sizes scaling alongside it, so the largest accessibility size still lays out. The platform's own target minimum — 44 pt on Apple platforms, 48 dp on Android — sits above 2.5.8's 24 CSS pixels, so a control that clears the criterion can still fail the guideline a native review applies; that is a suggestion under **A failure is a criterion**, never a ledger line.

## Evidence

- **Each claim states the run that produced it.** "Keyboard-operable" names the walk (which keys, which controls, what happened); "contrast passes" names the pair and the ratio against the right bar — 4.5:1, or 3:1 only for text at 24 CSS pixels, or 18.66 px bold, and 3:1 for the parts of a control that identify it or its state, never for a divider that only separates content — sampled from the rendered surface rather than read off the token wherever an overlay, opacity, gradient, tile, or image sits between the declared color and the pixel, since a token that passes can render a composite that fails; "scan clean" names the engine and the page state; a screen-reader or voice-control claim names the product and version, the browser, and the operating system it ran on, because the result is a property of that stack and goes stale when any part of it changes. For a stateful widget the run names the states it visited — open, closed, error, loading.
- **A run kind settles only what that kind can settle.** A grayscale or color-vision render settles 1.4.1, and information that disappears there was carried by color alone; a capture made with the reduced-motion preference emulated settles 2.3.3, which is AAA — so at an AA target it produces a suggestion and no ledger line — whereas reading the code path that would have run settles nothing at any level; an accessibility-tree inspection settles 4.1.2 and the heading and landmark structure; a text-spacing override settles 1.4.12; a capture under forced colors settles 1.4.1 and 1.4.11 for the cues and boundaries the forced palette repaints.
- **The grade is the evidence's, not the author's.** A read of the markup without a run is Flagged at most; an accessibility-tree inspection — computed name, role, and state taken from DevTools, a browser tool, or the platform's own tree in a simulator or a device dump — is a run, and settles nothing about what is announced; a screen-reader experience the author reasoned about rather than heard is Human-required — the presence of a live region is verifiable, what it announces is not. A Flagged finding is never hidden behind a Human-required or Verified line on the same criterion.
- **AAA is AAA.** A criterion's level is the one in the reference, and a real 2.2 number the reference does not list is AAA; naming an AAA criterion as the reason a change fails AA, or folding AAA items into an AA sign-off, misstates the target both ways. The project names its target level; the default is AA.
- **A failure is a criterion, not a taste.** A finding names the criterion it fails; a best practice with no criterion behind it is a suggestion, graded as one, and never counted among the failures.
- **Scans read as evidence, never as verdicts.** A scan detects a minority of the criteria, and for those only some failures — the rest of the ledger needs another run or the Human-required state. A scan's pass is a pass on its rules, and on the bytes it ran on — an edit after it is unscanned; its failure is a finding to confirm against the criterion it cites; a rule it does not have is not a criterion that passed; its "incomplete" or "needs review" bucket is a Flagged or Human-required line, never dropped; and its impact labels and scores are triage, never the ledger's state.
- **A run is a run.** A keyboard claim comes from key presses, not a scripted `focus()` walk, which fires no key handlers and proves reachability only.

## The criterion ledger

The change's summary — the commit or PR body — carries the ledger: one line per touched criterion, number and name, the state, and the evidence, the reason, or the handoff target. `Verified` names the run; `Flagged` names the finding; `Human-required` names the ability and the assistive technology that settle it (a screen-reader user on VoiceOver; a switch user), the flow already run, and that the ticket does not close before it does; `Not exercised` and `N/A` each say why in a clause. A ledger line with a state and neither evidence nor reason is not a line and is rewritten or dropped. A UI change that touches no criterion writes one line saying so, so the reader can tell "nothing touched" from "nobody looked". A change that alters what another repo renders, with no UI to run here, still writes its lines — Human-required or Not exercised, naming the rendering repo as the handoff. The ledger is closed: a criterion the change touched and the ledger does not mention is a Flagged line waiting to be written. The ledger is never averaged: a percentage score, a "mostly passes", or a count of passes over a count of criteria hides the Flagged line that decides whether the change ships. No line and no sentence anywhere says "fully accessible", "WCAG compliant", or "accessible" without a level and a ledger behind it.

## Boundary

This skill carries the building contracts and the evidence doctrine, and nothing derived from them. It is not a WCAG digest: the reference holds the number, name, and level of each A and AA criterion, and a technique or explanation added to a row is the regulation pack this skill refuses to become. It is not a report ceremony: the ledger lands in the change's summary, and no audit document, test plan, or sign-off form is demanded before delivery. It is not a persona generator: it never narrates what a screen-reader user will hear, feel, or struggle with — a run reports what the technology did, and a person reports the rest. It is not a scanner wrapper: which engine, which rule set, which CI step, and which component library are the project's convention skill's. A VPAT or ACR is a compliance document derived from ledgers and is written elsewhere; PDF accessibility is a different artifact and toolchain. A rule above answered "no" for this change is a finding on it, the same as a failing check — graded against the criterion that rule names, or, where it names none, as a suggestion under **A failure is a criterion** and never counted among the failures.
