# Accessible UI

A **success criterion** is one numbered WCAG 2.2 requirement at level A, AA, or AAA; the number and name of every A and AA criterion, with its level, is in [references/criteria.md](references/criteria.md), and a real 2.2 number absent from that list is AAA. A criterion is **touched** by a change when the change creates, alters, or removes something the criterion governs: a new button touches 2.1.1 Keyboard and 4.1.2 Name, Role, Value; a color tweak touches 1.4.3 Contrast and 1.4.11 Non-text Contrast; a CSS comment edit or a variable rename touches nothing. A criterion is **exercised** when a run was made against it. **Evidence** is a run — a keyboard walk, a screen-reader pass, a scan, a contrast measurement, a grayscale or color-vision render, a capture under an emulated preference, an accessibility-tree inspection, a text-spacing override — named by what ran and what it found, or, for a Flagged line only, a read that names the line and the criterion it fails; a belief about what the markup should do is not evidence. The **ledger** is the closed list, one line per touched criterion, in which each ends in exactly one of five states and none is silent: **Verified** (a run confirmed it), **Flagged** (a run or a read found a likely failure), **Human-required** (only a person using the assistive technology can settle it), **Not exercised** (touched, and no run was made), **N/A** (touched, and the criterion's condition does not arise in this change). The first three are the **grades**, the states evidence can support; when two runs support different grades, Flagged wins over Human-required, and Human-required wins over Verified; and where a criterion's states were only partly reached — a dialog whose open state was walked and whose error state was not — the line is **Not exercised**, never Verified on the strength of the states that were.

The test every rule serves: a person who cannot see the pointer, cannot use one, or hears the page instead of seeing it can **reach, understand, operate, and leave** every control the change touches, and the change's author has said exactly what they checked. The hard stop: never write "accessible", "fully accessible", or "WCAG compliant" anywhere without a level and a ledger behind it.

## Building

Every control carries what the default output skips when nobody asks; the contracts for the widgets it skips most are [references/patterns.md](references/patterns.md)'s, opened when the change builds or alters one of them — a chip, a field or its label, a live region, a dialog, a hover menu, a composite, a card, a table, a chart, an image or icon, or a binding submission — their native (SwiftUI/UIKit) lines [references/native.md](references/native.md)'s, opened only on a native change and never on a web one.

- **Reach for the most proven implementation first.** An accessible component this codebase already has, then the project's component library, then a native element, then a native element plus the minimum ARIA, and a custom widget only with its full keyboard, focus, and state behavior built end to end. ARIA that restates what the native element or the library primitive already exposes (`aria-required` on a `required` input, `role="button"` on a `<button>`, a `tabindex` on a headless-library menu item) is noise, ARIA that contradicts it is a bug, and ARIA the element cannot carry — an `aria-label` on a `<div>` with no role — is neither: it is nothing.
- **Name, role, state, in the accessibility tree — not in the pixels.** A control's exposed state flips with its look in the same update (the chip and composite contracts — tabs, toolbars, disclosures — are patterns.md's); a disabled control is `disabled` or `aria-disabled`, not grayed by class alone — `aria-disabled` when the reason it is off is the message the person has to reach, or when the control is only momentarily inert and native `disabled` would drop the waiting person's focus to the body; native `disabled` when the control is inert for the life of the view and there is nothing to explain. The visible look and the exposed state change together or the control lies to one audience.
- **A label is a label.** Give every field, search box, and icon-only button a real name — `<label for>`, `aria-label`, or `aria-labelledby`, never `placeholder` and never `title` alone (patterns.md's field contract, opened when the change adds or alters a field or its label). Contain the visible text of a label in its accessible name, so voice control can say it (2.5.3) — and keep names distinct on a screen (a card's "Edit" carries the card's name), so voice control can say which.
- **The keyboard reaches what the pointer reaches, in the order the eye reads.** Give hover-only reveals, drag-only reorders, and swipe-only dismissals each a keyboard path; the tab order follows the DOM, and the DOM follows the visual order — a `tabindex` above zero is a bug. A composite is one stop with arrow keys inside it, and an interactive part nested in it (a clear button, a chip's close) is its own stop — patterns.md's contract; a live region is never a stop.
- **Focus is never lost.** A dialog's focus contract — move in, trap, `inert` the rest, return to the opener — is patterns.md's; before removing a focused element, move focus to the nearest remaining sibling or to the container; on a route change, put focus on the new heading or main and set `<title>` to the new screen's name — the title is what the history entry and the tab carry, and the focus move is what gets announced, which is why the rule is both and not either.
- **Focus is visible.** Every focusable element shows an indicator in every theme (the 3:1 bar and the sticky-header contract are patterns.md's); `outline: none` without a replacement is a failure, and a `box-shadow` ring vanishes under forced colors, so pair it with a transparent `outline` the forced palette repaints.
- **Status is announced by a region that already exists** — rendered empty first, text set later; the live-region contract is patterns.md's. Announce the outcome ("3 results"), not the mechanics, and never the same text twice for one event; a change either moves focus or announces, never both.
- **The rendered surface carries its own contracts.** Color and forced colors, motion and timing, target size and pointer behavior, text structure and language, and text scaling: [references/surface-and-content.md](references/surface-and-content.md), opened when the change alters color, contrast, motion, timing, target size, pointer behavior, heading, list, or table structure, language, layout, type, spacing, the viewport meta, or a destructive, binding, or financial submission.

## Evidence

- **Each claim states the run that produced it.** "Keyboard-operable" names the walk (which keys, which controls, what happened); "contrast passes" names the pair and the ratio against the right bar — 4.5:1, or 3:1 only for text at 24 CSS pixels, or 18.66 px bold, and 3:1 for the parts of a control that identify it or its state, never for a divider that only separates content — sampled from the rendered surface rather than read off the token wherever an overlay, opacity, gradient, tile, or image sits between the declared color and the pixel, since a token that passes can render a composite that fails; "scan clean" names the engine and the page state; a screen-reader or voice-control claim names the product and version, the browser, and the operating system it ran on, because the result is a property of that stack and goes stale when any part of it changes. For a stateful widget the run names the states it visited — open, closed, error, loading.
- **A run kind settles only what that kind can settle.** A grayscale or color-vision render settles 1.4.1, and information that disappears there was carried by color alone; a capture made with the reduced-motion preference emulated settles 2.3.3, which is AAA — so at an AA target it produces a suggestion and no ledger line — whereas reading the code path that would have run settles nothing at any level; an accessibility-tree inspection settles 4.1.2 and the heading and landmark structure; a text-spacing override settles 1.4.12; a capture under forced colors settles 1.4.1 and 1.4.11 for the cues and boundaries the forced palette repaints.
- **The grade is the evidence's, not the author's.** A read of the markup without a run is Flagged at most; an accessibility-tree inspection — computed name, role, and state taken from DevTools, a browser tool, or the platform's own tree in a simulator or a device dump — is a run, and settles nothing about what is announced; a screen-reader experience the author reasoned about rather than heard is Human-required — the presence of a live region is verifiable, what it announces is not. A Flagged finding is never hidden behind a Human-required or Verified line on the same criterion.
- **AAA is AAA.** A criterion's level is the one in [references/criteria.md](references/criteria.md), opened when a level is being determined for a ledger line or a 2.2 number absent from that list has to be graded; its header owns the misuse rules. The project names its target level in the convention skill or `CLAUDE.md`; the default is AA.
- **A failure is a criterion, not a taste.** A finding names the criterion it fails; a best practice with no criterion behind it is a suggestion, graded as one, and never counted among the failures.
- **Scans read as evidence, never as verdicts.** A scan is evidence on its rules and the bytes it ran on, never a verdict — read one by [references/reading-a-scan.md](references/reading-a-scan.md).
- **A run is a run.** A keyboard claim comes from key presses, not a scripted `focus()` walk, which fires no key handlers and proves reachability only.

## The criterion ledger

The change's summary — the commit or PR body — carries the criterion ledger: one line per touched criterion, number and name, the state, and the evidence, the reason, or the handoff target. `Verified` names the run; `Flagged` names the finding; `Human-required` names the ability and the assistive technology that settle it (a screen-reader user on VoiceOver; a switch user), the flow already run, and that the ticket does not close before it does; `Not exercised` and `N/A` each say why in a clause. A ledger line with a state and neither evidence nor reason is not a line and is rewritten or dropped. A UI change that touches no criterion writes one line saying so, so the reader can tell "nothing touched" from "nobody looked". A change that alters what another repo renders, with no UI to run here, still writes its lines — Human-required or Not exercised, naming the rendering repo as the handoff. The ledger is closed: a criterion the change touched and the ledger does not mention is a Flagged line waiting to be written. The ledger is never averaged: a percentage score, a "mostly passes", or a count of passes over a count of criteria hides the Flagged line that decides whether the change ships.

## Boundary

This skill carries the building contracts and the evidence doctrine, and nothing derived from them. It is not a WCAG digest: the reference holds the number, name, and level of each A and AA criterion, and a technique or explanation added to a row is the regulation pack this skill refuses to become. It is not a report ceremony: the ledger lands in the change's summary, and no audit document, test plan, or sign-off form is demanded before delivery. It is not a persona generator: it never narrates what a screen-reader user will hear, feel, or struggle with — a run reports what the technology did, and a person reports the rest. It is not a scanner wrapper: which engine, which rule set, which CI step, and which component library belong to the project's convention skill for the `accessibility` role, named in `CLAUDE.md`'s `## Convention skills` block; where none exists, apply every rule above to what this change needs and raise the missing project answer as a finding. What data may appear in an accessible name, label, or announcement is `phi-safe-code`'s — a member ID renders into the accessibility tree like any other sink. A VPAT or ACR is a compliance document derived from ledgers and is written elsewhere; PDF accessibility is a different artifact and toolchain. A rule above answered "no" for this change is a finding on it, the same as a failing check — graded against the criterion that rule names, or, where it names none, as a suggestion under **A failure is a criterion** and never counted among the failures.
