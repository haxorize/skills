# Gradle

Open this only when the repo builds with Gradle. Gradle ships none of the four primitives the workflow takes from the tool elsewhere — no outdated command, no audit command, no lockfile by default, and no registry field for provenance — so each step's substitute is here rather than threaded through the body.

## Discovery has no built-in command

Outdated comes from the versions plugin (`io.github.ben-manes.versions`), whose task is `./gradlew dependencyUpdates`. A build that never applied it — the majority case — has no outdated source at all: report that absence as a finding and fix the step list from the version catalog and the changelogs, never by adding the plugin to a repo that did not ask for it. Where it is applied, read its `revision` and `rejectPreReleases` settings before trusting the targets. The plugin has defaulted `rejectPreReleases` to `true` since v0.61.0, so a current plugin reports a package whose only newer release is a pre-release as up to date — unless the current version is itself a pre-release, in which case newer pre-releases are still reported, or `revision` is `integration`, under which the flag reads `false`; an older plugin, or a build that set the flag false, proposes the `-RC1` as a target — a step this skill never sanctioned, struck by hand before the step list is fixed. A build may filter instead with a `rejectVersionIf` block inside `tasks.named<DependencyUpdatesTask>("dependencyUpdates")`, over an `isNonStable()` the build script defines itself; grepping for either name finds nothing in a build that simply left the defaults alone, so absence of the names is not absence of the guard.

Vulnerabilities come from whatever scanner the repo already runs — the OWASP plugin's `./gradlew dependencyCheckAnalyze`, `osv-scanner` over `gradle.lockfile` or, where locking is off, over the `gradle/verification-metadata.xml` the Provenance bullet below already has the run generate, the platform's advisory feed. A repo with none has no source for the security-flagged class at all: every package is then classed on its changelog alone, the run has no security-first step to put first, and the close names the run as one that ran with no vulnerability source at all. That absence is a finding to report, never a step quietly dropped for want of a command. **Before leaving step 1, capture `./gradlew dependencies` in full.** Where the build has no locking (§ Step 4), that capture is the only record of the transitive set as it stood, and after the bump it cannot be recovered.

## The manifest may not pin

The version catalog `gradle/libs.versions.toml` is the manifest where the repo keeps one; otherwise the versions sit in each `build.gradle` or `build.gradle.kts`, and the step list is fixed over both.

A dynamic version (`1.+`, `latest.release`) or a changing version (a `-SNAPSHOT`) resolves differently on different days, so the *from* of a from → to is whatever resolved last and not what the manifest says. Read the resolved version from `./gradlew dependencies` before the bump, and report the selector itself as a finding: `configurations.all { resolutionStrategy { failOnNonReproducibleResolution() } }` is what closes it — `failOnDynamicVersions()` covers only the dynamic half and leaves every `-SNAPSHOT` open, and `resolutionStrategy` is a per-configuration property, so a bare top-level block resolves against nothing. Until it closes, no audit in step 2 binds the version that will actually build.

## Step 2 has no registry attestation field

- **Publisher** — the coordinates plus the PGP key that signed the artifact. Maven Central verifies namespace ownership when the namespace is *registered*, so a `groupId` that changed between the current version and the target is the shape this bullet looks for; a signing key that changed under an unchanged `groupId` is the other. Both rest on the same PGP material the Provenance bullet reads, so on Gradle — as on PyPI, and unlike npm and NuGet — publisher and provenance are one fact, not two, and `Unattested publishers: accept` clears them together.
- **Publish age** — Gradle reports versions without dates, so the release date step 2's floor needs comes from the repository, not the build. Read the target artifact's own `Last-Modified` header (`curl -sI https://repo1.maven.org/maven2/<group, dots as slashes>/<artifact>/<version>/<artifact>-<version>.jar`), or the dated directory listing one level up. Two lookups that look right and are not: Central's `solrsearch` API carries a `timestamp` per version, but its `gav` index has been frozen since mid-2025 and returns `numFound: 0` for any current release — valid JSON, no error, no date for the target you are actually bumping to; and `maven-metadata.xml`'s `<lastUpdated>` is one directory-level stamp that dates the newest version only. Without a per-version date the floor is unevaluable and the package defers rather than passing unchecked.
- **Provenance** — Gradle's dependency verification is the check, in place of a registry attestation field. `./gradlew --write-verification-metadata sha256,pgp` writes `gradle/verification-metadata.xml`. **A file generated after the bump attests nothing about the bump**: bootstrapping trusts whatever is in the repositories already, and in Gradle's own words, if a malicious dependency has already been introduced "Gradle will record the compromised artifact's checksum or signature." Central also copies an optional `<filename>.sigstore.json` sibling where the publisher signs that way, which is a stronger provenance fact than a PGP key; adoption is thin, so its absence proves nothing and its presence is worth recording. Generate before the bump, bump, then read the diff — a new `<pgp>` key, or a checksum-only entry where the package previously carried a signature, is the attested-then-unattested regression [version-gates.md](version-gates.md) § Unattested publishers holds at **Review** under every `Unattested publishers:` value.
- **Tarball diff** — unzip the two `.jar` files and diff, reading the published `-sources.jar` where it carries sources: a compiled class-file diff reports every recompilation as a change and buries the one that matters, and Central allows a placeholder `-sources.jar` and suggests it carry a README, so a non-empty jar proves nothing: check it holds `.java` or `.kt` sources before trusting it as the readable diff.
- **License** — the `<licenses>` element of the target's own `.pom`, fetched as a sibling of the jar in the repository (`.../<group, dots as slashes>/<artifact>/<version>/<artifact>-<version>.pom` — `com.squareup.okhttp3` is `com/squareup/okhttp3`), never unzipped from the jar: the embedded `META-INF/maven/**/pom.xml` is Maven Archiver's default and Gradle-built jars carry none. Read the target's POM rather than the project's README or a rendered registry page.

## Step 3: the wrapper and the toolchain are two different majors

The Gradle version lives in `gradle/wrapper/gradle-wrapper.properties`, in `distributionUrl`. `./gradlew wrapper --gradle-version <v>` updates that file and leaves `gradle-wrapper.jar` at the old version — running the task once "will update `gradle-wrapper.properties` only, but leave the Wrapper itself in `gradle-wrapper.jar` untouched." That old jar still reads `distributionUrl` and downloads and runs the *new* distribution, so nothing runs or reports the wrong Gradle version; what one run leaves behind is stale wrapper files. Run the task a second time so all of them match, and commit every one. Where `gradle-wrapper.properties` pins `distributionSha256Sum` — the posture this skill assumes — the task fails outright unless a sum is supplied — `--gradle-distribution-sha256-sum <sum>` on the run, or the task's own `distributionSha256Sum` property — and that sum is re-pinned to the new release's as part of the bump. A run that does not change the Gradle version preserves the existing pin instead.

The Java version the build targets — `java { toolchain { languageVersion = JavaLanguageVersion.of(<n>) } }` — is a different thing from the JDK running Gradle, and bumping either is not bumping the other. Each is its own major step, in the toolchain-first order § 3 sets.

## Step 4: locking is opt-in

Dependency locking is off unless the build declares `dependencyLocking { lockAllConfigurations() }` or activates it per configuration with `resolutionStrategy.activateDependencyLocking()` — grepping for the first name alone reports a build locked the second way as unlocked. Only then does a build resolve against stored lock state and fail where the resolution no longer matches — the `npm ci` equivalent § 4 asks CI for. `./gradlew dependencies --write-locks` does **not** lock a multi-project build: `dependencies` runs on one project, typically the root, so every subproject stays unlocked while the close reports a lockfile diff. Locking the whole build takes a task that resolves every resolvable configuration across all projects, which Gradle's dependency-locking guide gives as `resolveAndLockAll`; run `./gradlew resolveAndLockAll --write-locks` — the guide's task asserts that flag and fails without it — and check a `gradle.lockfile` exists per project before believing the build is locked.

With locking off there is no lockfile and no diff to read. The close's from → to then comes from the version-catalog or build-script diff for what the manifest names, and from the `./gradlew dependencies` captures the discovery section above requires before and after — root-project only unless the run resolved every project, which the close states either way. Report the absent locking as a finding at the close: a run that cannot show what the transitive set became has audited the manifest and not the build, and the close's table says which it did.
