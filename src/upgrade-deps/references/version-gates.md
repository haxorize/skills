# Version gates

Two branch-gated rules for `upgrade-deps`, each opened from the steps that name it — the release-age gate from step 1 and again from step 2.

## Registry release-age gate

Reached wherever step 1 found an enforced or a declared floor at all — a `Minimum release age:` in the repo's `CLAUDE.md` `## Registry` block, naming a curating proxy that refuses packages younger than it, or a floor the package manager itself enforces. It opens whether or not that floor raises step 1's maximum, since what it governs is what the discovery command withheld, not what step 2 audits at — and on pnpm 11+ the manager enforces a day unprompted, well under the default. Below the maximum a target is held by this skill, and below a *proxy's* number it is also unfetchable, since the proxy will not serve it. A *manager's* floor is weaker than it looks and is not a second refusal: pnpm's default is non-strict, so where no in-range release clears it pnpm installs the young one anyway and appends it to `minimumReleaseAgeExclude` in `pnpm-workspace.yaml` — a tracked file mutated as a side effect of install, with only a line on stdout to say so. Only `minimumReleaseAgeStrict: true` makes it refuse, with `ERR_PNPM_NO_MATURE_MATCHING_VERSION`. An unexplained `minimumReleaseAgeExclude` entry in the bump's diff is pnpm's writing rather than the run's; it comes out in the same step that put the bump in, alongside any entry the run added deliberately below. Step 2's retarget runs against the maximum, and a package with no release clearing it defers with a review-by date of publish date plus that maximum.

Where the floor is the manager's, step 1's `outdated` table is a candidate list at the manager's threshold rather than an answer at that maximum, and what the manager withheld is absent rather than marked — `pnpm outdated` drops every release younger than `minimumReleaseAge` and says nothing. Re-run the command with the floor off and diff the two lists: `pnpm --config.minimum-release-age=0 outdated`, kebab-case, which holds on pnpm 10, 11, and 12. The camelCase `--config.minimumReleaseAge=0` is parsed and discarded in silence on pnpm 12 — no warning, no error, and no exit-code tell either, since `pnpm outdated` exits 1 whenever anything is outdated whichever spelling ran — so it returns the unflagged list's twin and the diff reads clean when nothing was compared. The table's contents are the only signal, and camelCase still works on pnpm 10 and 11, so a habit formed there breaks invisibly on 12. On npm the same re-run is `npm outdated --min-release-age=0`. The one withheld release the run would still have taken is a security fix, which step 2's floor exempts and the manager does not: an `npm audit fix` the window blocks leaves the package *at* a vulnerable version rather than at the same one — it takes the newest release inside the window, still inside the advisory's range — warns that the fix was published after the cutoff, and exits non-zero. The lockfile therefore shows a version change that is not a fix; the warning and the exit code are the reliable tells, never the diff. The way through is that manager's exclude list, never a floor relaxed for the whole tree — and the entry comes back out once the bump lands, since a package left on it carries no enforced floor into any later run. Both edits touch a target-repo config file rather than the manifest, so they ride in that security step's own commit and the close's table names them — the step-1 ask counts steps and has no slot for them.

## Unattested publishers

Reached only by a package whose target carries no registry attestation and whose other checks are clean. The `## Registry` key `Unattested publishers: accept | ask | defer` settles it: `accept` takes the package on the tarball-versus-changelog result, recorded in the close, and clears the attestation together with the publisher identification that rests on it — on PyPI those are one fact, since the attestation is the only publisher source there. It never reaches a Publisher check that failed on its own: a lookup that errored, or the new or unknown account that bullet routes to **Review** and **Defer**, is untouched by this key, and on npm and NuGet the publisher is readable whether or not the release is attested; `defer` writes it to `docs/deps-deferred.md` ending `; no review-by date` in place of the date, since no date retires a missing attestation; `ask` — the value when the key is absent — puts the whole Review set to the user in one table at the end of step 2, each row carrying that tarball-versus-changelog result and any trusted-publishing workflow the source repo shows (`id-token: write` and a publish step), the evidence the user accepts in place of the registry's. The key never covers a target whose *previous* version was attested: that regression is **Review** under every value, because it is the one shape the attestation exists to catch.
