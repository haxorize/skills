# Ship is its own user-invoked skill, not `implement`'s tail

The main flow ended at a step nothing owned — `which-skill` listed "6. Ship." while every other step named a skill — and the beat's outbound prose is where unverified claims landed (a closing comment asserting commits were unreviewed, forcing a correction). **Ship** becomes a user-invoked skill carrying a green, reviewed change to a closed Ticket: commits in **Commit order**, push, then a closing comment — and, where the change needs one, a branch, a PR, and a merge — with every claim in that prose checked against evidence (scope against the diff, review and coverage claims against `git log <base>..HEAD`) before it is written, and with each outward act *yielding* the exact command when the environment blocks it rather than retrying around it. **Whether a PR exists at all turns on whether another person must approve the change, not on which host it lives on**: an approver means a branch and a PR, none means it lands on the trunk directly. Keying that fork to the host was rejected because it gets the common case backwards — a solo GitHub repo would manufacture a branch and a PR for the author to approve alone, which is ceremony wearing review's clothes; keying it to the approver makes the no-PR path first-class, and it is the majority path for the work this skill actually sees. Appending the beat to `implement` was rejected because a repo with no tracker never runs `implement` — this repo has neither an `Issue tracker:` block nor issue refs in its commits, yet ships constantly in ordered chunks, so the rule would never fire on a large share of the work it exists for. Extracting a general "verify before asserting" behavior was rejected because its trigger would be every turn, and the failures are gate-shaped: the gates that write durable prose already verify against different evidence each (`capturing-learnings` that cited paths resolve, `handoff` that state matches the live repo, `review-changes` that a HIGH finding quotes `file:line`).

## Consequences

- `implement` *suggests* `ship` the way it already suggests `review-changes` — both user-invoked, so neither can invoke the other.
- Ship owns the **claims** discipline; per-repo commit-message and PR-body *style* stays in each repo's CLAUDE.md. A consuming repo that documents neither (a11y-health today) has its own gap, not this suite's.
- The suite gains a skill whose payload is mostly verification and plumbing. If it stays thin after real use, the fallback is folding it back into per-repo convention — a deletion, not a redesign.
- The related "claimed a step ran that never ran" failure is *not* covered here: `write-skill`'s Load-gate carve-out exempts built-ins because they cannot fail to load, which reasons from availability rather than execution. Repairing that carve-out is its own change.
