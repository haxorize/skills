# The review-receipt hook gates a push on a review report in the landing zone

## Context

Twice on 2026-08-22 a batch of this repo was pushed to `main` before any `review-changes` report covered it — what disk shows is each report's mtime against its push: B5 (`d5c671b`, pushed 15:01; `skills-2026-08-22-b5.review.md` written 15:22, after an in-session subagent had reviewed an earlier tree and written no file, so the grill's edits after it reached the remote unreviewed) and B6 (`e913c39`, pushed 15:55; `skills-2026-08-22-b6-records.review.md` written 16:20, the batch's handoff having dropped the review step). That the user, not the session, noticed each time is the transcript's account, not something the files can show. The gate existed in prose in two places, and neither was in force at the commit: `committing`'s claims table ("reviewed" needs a report path or the user's exact skip phrase; silence is a stop) binds only while that skill is loaded, and both sessions committed with bare `git commit`; the batch plan's per-batch instruction (finish with `/review-changes` and the pruning lens, then `/address-findings`) lives outside the repo, and the session read the handoff instead, which had dropped the step. `Landing:` says trunk, no PR, push pre-authorized, so nothing downstream stopped it either. The escalation row [ADR-0051](0051-usage-evidence-mining-round.md) gave `write-skill` — prose, then hard prohibition, then hook or lint, each step justified by an observed failure — has its two observed failures.

## Decision

- **A third hook, `review-receipt.sh`**, a `PreToolUse` check on Bash: a `git push` from a directory whose nearest `CLAUDE.md` (walking up to the repo top) carries `Review required: yes` is refused unless every source tree the push would send equals a `Reviewed-tree: <40-hex>` stamp in a `<repo>-<date>-*.review.md` report in the landing zone (`handoff`'s "Where to write it"). A source is each refspec's source, else `HEAD`; the hook header is the contract for the forms. The report is the receipt, and only `review-changes` and `address-findings` write the stamp, so a subagent review that wrote no file is not a review the hook can see — on purpose.
- **The receipt is keyed on content, not time.** `review-changes` stamps the hash of the work tree it reviewed (a throwaway index seeded from `HEAD` over `git add -A :/`, so uncommitted and untracked non-ignored files count, and a tracked-but-ignored one still does). Every `address-findings` pass appends one more stamp, of the tree as the pass leaves it, with no condition: a pass that changed nothing appends a second stamp equal to the first, because the appended line is also the pass's close marker that `committing`'s `next-step.sh` reads. The hook passes a push when the tree of each commit it sends equals any stamp in a matching report. The thing pushed is the thing reviewed, byte for byte, in whichever order the commits were made; a message-only amend and a content-free rebase keep the tree and pass.
- **The order is review the tree, fix, commit, push.** [ADR-0080](0080-commit-per-batch-review-per-family.md) sets the grain inside that order: a commit per batch, unreviewed, a review per batch family, and the review's fixes as their own commit; the last `Reviewed-tree:` must equal the tree pushed.
- **Opt-in by repo, through the `Landing:` key**, which grows a sixth line, `Review required:` (`yes`/`no`; missing means `no`). `committing` reads it like the other five; `onboard-repo` writes it.
- **The skip path is the user's own push.** `! git push` in the prompt, or any terminal, never passes through a tool hook. No flag, no phrase, no environment variable: an agent has no legitimate reason to push unreviewed work, and the user always has the keyboard. The one agent-side act that satisfies the check is a hash written into a report by hand, which the hook cannot tell from a computed one — a fabricated receipt, and `committing`'s claims rule is what it fails, not this hook.
- **`handoff`'s Next-steps rule carries the review line**: in a `Review required: yes` repo, a path that ends in a push names the review and fix steps before it, so a handoff cannot drop them the way the B6 handoff did.
- **Depending skill:** `committing` — its "reviewed" claim row names the report as the evidence in a `Review required: yes` repo, and the hook is that row's mechanical half at the push. The hook reads `handoff`'s landing-zone definition through `landing.sh`; that is a consumer relation, not a dependant, so `handoff` is not on the `Depends:` line.
- **The hook reads the repo the push runs in**, not the session's directory: `cd <dir> &&`, `git -C <dir>` and the other forms the hook header lists move it, and that repo's top-level `CLAUDE.md` alone carries the `Review required:` line that decides; a push sends the whole branch, so a subdirectory's `CLAUDE.md` never opts out, and a top-level file the hook cannot read holds the push. The line belongs in the `Landing:` block but is read anywhere in the file outside a fence; the hook does not scope to the block. The B6 review's bypass rows (a trailing `# -n`, a brace group, `cd ../repo && git push`, a second remote) are in the selftest.
- **The push shape is the shared lib's.** How a push may be spelled is `hook-lib.sh` / `hook-lib.py`, extracted with the rename-safety tokenizer port ([ADR-0054](0054-commit-bypass-hook-always-on.md)); this hook holds only the push shape and the receipt check, and keeps one reading the lib does not take, `git -C <dir>` moving the push directory, since only the receipt check cares where the push runs. The shared selftest harness is `selftest-lib.sh`, and the hook rosters in `install.sh` and `post-merge` derive from each hook's `# Install note:` header line.

## Considered Options

- **A sixth global rule instead** — rejected: prose has failed twice at this exact act, and the admission rule says a rule a hook could enforce belongs in `hooks/`.
- **Gate `git commit` as well** — rejected: it would block the fix-up commits `address-findings` produces after the review; the push is the act that leaves the machine.
- **Always on, like `commit-bypass`** — rejected: a repo with a PR-and-approver flow has its review on the PR, and a scratch repo has none; the repo's `Landing:` key is where that is already declared.
- **A skip flag or phrase the agent can pass** — rejected: it recreates the `--no-verify` shape [ADR-0054](0054-commit-bypass-hook-always-on.md) blocks.
- **Key the receipt on time: a report at least as new as the oldest unpushed commit.** Tried first and rejected the same day. The user's order is review the tree, fix, commit, push, and a time rule refuses it by design, since a report written before the commits it covers is older than all of them. It also let a `touch`ed report pass, and it could not see edits made after a review and folded into a later commit.

## Consequences

- A push through the Bash tool in a gated repo needs a report whose stamp equals the tree being sent. Any edit after the last stamp, a one-character typo included, blocks until re-stamped, which is why every `address-findings` pass appends a stamp.
- The stamp folds in every untracked file `.gitignore` does not exclude, so a scratch file sitting in the tree at review time has to be deleted or ignored, and the tree re-stamped, before the push passes. Committing it to satisfy the gate is the wrong move for a scratch file and the wrong move twice for a secret; `review-changes`' tree-stamp reference makes clearing untracked files before the stamp a stop.
- What the hook cannot see: whether `review-changes` computed the stamp. A hand-typed hash matches as well as a real one, and `committing`'s claims rule is what catches it.
- The gate is cleared only by a human keystroke: `/review-changes` and `/address-findings` are user-invoked ([ADR-0015](0015-model-invoked-vs-user-invoked-split.md)), so the block message asks the model to ask for them, and the model reports a blocked action.
- The hook fails open on its own errors, as [ADR-0053](0053-global-rules-layer.md) sets for every hook, except for two fail-closed arms in a gated repo, recorded there as an exception: a source tree git cannot resolve, and a stamp reader or `landing.sh` that is missing from the checkout or fails. Either holds the push, because a copy of the hook made outside the checkout would otherwise ungate every push.
- `install.sh` prints the hook in its snippet, `post-merge` runs its selftest, and `global/README.md` states the contract.
- A report written before stamps existed carries none, so the first push in a gated repo after the change needed a fresh `/review-changes`; the block message names the remedy.

## Deferred

- **Revisit the gate** when a re-stamp is demanded for a change the user would have waved through more than once a week, or when a review report is found to have been written solely to satisfy the hook.
