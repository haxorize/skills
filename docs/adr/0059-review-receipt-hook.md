# The review-receipt hook gates a push on a review report in the landing zone

## Context

Twice on 2026-08-22 a batch of this repo was pushed to `main` before any `review-changes` report covered it — what disk shows is each report's mtime against its push: B5 (`d5c671b`, pushed 15:01; `skills-2026-08-22-b5.review.md` written 15:22, after an in-session subagent had reviewed an earlier tree and written no file, so the grill's edits after it reached the remote unreviewed) and B6 (`e913c39`, pushed 15:55; `skills-2026-08-22-b6-records.review.md` written 16:20, the batch's handoff having dropped the review step). That the user, not the session, noticed each time is the transcript's account, not something the files can show. The gate existed in prose in two places, and neither was in force at the commit: `committing`'s claims table ("reviewed" needs a report path or the user's exact skip phrase; silence is a stop) binds only while that skill is loaded, and both sessions committed with bare `git commit`; the batch plan's per-batch instruction (finish with `/review-changes` and the pruning lens, then `/address-findings`) lives outside the repo, and the session read the handoff instead, which had dropped the step. `Landing:` says trunk, no PR, push pre-authorised, so nothing downstream stopped it either. The escalation row [ADR-0051](0051-usage-evidence-mining-round.md) gave `write-skill` — prose, then hard prohibition, then hook or lint, each step justified by an observed failure — has its two observed failures.

## Decision

- **A third hook, `review-receipt.sh`**, a `PreToolUse` check on Bash: a `git push` from a directory whose nearest `CLAUDE.md` (walking up to the repo top) carries `Review required: yes` is refused unless a `<repo>-<date>-*.review.md` in the landing zone (`handoff`'s "Where to write it") is at least as new as the oldest commit in the range the push would send — `<remote>/<dst>..HEAD` when the command names a remote and destination, else `@{upstream}..HEAD`, else `origin/<branch>..HEAD`; the hook header is the contract for the forms. The report is the receipt; `review-changes` is the only thing that writes one, so a subagent review that wrote no file is not a review the hook can see — on purpose.
- **The oldest unpushed commit decides**, not the newest: fix-up commits made after the review pass; a report older than the first unpushed commit reviewed a different tree and blocks.
- **Opt-in by repo, through the `Landing:` key**, which grows a sixth line, `Review required:` (`yes`/`no`; missing means `no`). `committing` reads it like the other five; `onboard-repo` writes it.
- **The skip path is the user's own push.** `! git push` in the prompt, or any terminal, never passes through a tool hook. No flag, no phrase, no environment variable: an agent has no legitimate reason to push unreviewed work, and the user always has the keyboard. The one agent-side act that satisfies the check is writing a file into the landing zone (`touch <zone>/<repo>-<date>-x.review.md`), which no rule examines — a fabricated receipt, and `committing`'s claims rule is what it fails, not this hook.
- **`handoff`'s Next-steps rule carries the review line**: in a `Review required: yes` repo, a path that ends in a push names the review and fix steps before it, so a handoff cannot drop them the way the B6 handoff did.
- **Depending skill:** `committing` — its "reviewed" claim row names the report as the evidence in a `Review required: yes` repo, and the hook is that row's mechanical half at the push. The hook reads `handoff`'s landing-zone definition; that is a consumer relation, not a dependant, so `handoff` is not on the `Depends:` line.
- **The hook reads the repo the push runs in**, not the session's directory: `cd <dir> &&` and `git -C <dir>` move it, and the nearest `CLAUDE.md` from that directory up to the repo top carrying a `Review required:` line decides, either value — `no` under a gated root opts a package out. The line belongs in the `Landing:` block but is read anywhere in the file outside a fence; the hook does not scope to the block. The B6 review's bypass rows (a trailing `# -n`, a brace group, `cd ../repo && git push`, a second remote) are in the selftest.

## Considered Options

- **A sixth global rule instead** — rejected: prose has failed twice at this exact act, and the admission rule says a rule a hook could enforce belongs in `hooks/`.
- **Gate `git commit` as well** — rejected: it would block the fix-up commits `address-findings` produces after the review; the push is the act that leaves the machine.
- **Always on, like `commit-bypass`** — rejected: a repo with a PR-and-approver flow has its review on the PR, and a scratch repo has none; the repo's `Landing:` key is where that is already declared.
- **A skip flag or phrase the agent can pass** — rejected: it recreates the `--no-verify` shape [ADR-0054](0054-commit-bypass-hook-always-on.md) blocks.
- **Extract the shared `hook-lib.sh` now**, as [ADR-0054](0054-commit-bypass-hook-always-on.md) scheduled for the third hook — not taken; see Deferred.

## Consequences

- A push from this repo through the Bash tool needs a report newer than the first unpushed commit. The review report's mtime is the receipt, so a report written and then edited still counts; a report copied in from elsewhere counts too — the hook checks presence and recency, not content, and the content check stays `committing`'s.
- What the hook cannot see: edits made after a review and folded into commits that an older-but-still-newer-than-range report covers. `review-changes`' reviewed-head stamp and `committing`'s "N commits since" line carry that in prose.
- **The order is commit, then review, then fix up, then push.** The receipt must be at least as new as the oldest unpushed commit, so a report written before the commits it covers exist is older than all of them and blocks — reviewing the uncommitted tree and committing afterwards, the order the B6 session used, is refused by design; `/ship`'s split is committed first and reviewed as commits. A rebase rewrites committer times and has the same effect: `git pull --rebase` after a review re-requires one, or the user's own push. Accepted as the cost of a rule the hook can check; the "written solely to satisfy the hook" trigger under Deferred is the signal that it is too high.
- The gate is cleared only by a human keystroke: `/review-changes` and `/address-findings` are user-invoked ([ADR-0015](0015-model-invoked-vs-user-invoked-split.md)), so the block message asks the model to ask for them, and the model reports a blocked action.
- `install.sh` prints all three hooks in one snippet; `post-merge` runs the third selftest; `global/README.md` states the contract.

## Deferred

- **The `hook-lib.sh` extraction.** This record overrides ADR-0054's schedule: the third hook shipped with the payload parse and segment scan copied and extended (comment and brace handling, cwd tracking), because the extraction touches two selftested hooks and the scanners now differ in three places. The trigger moves to the rename-safety tokeniser port, where all three scanners are in hand; ADR-0054 carries the dated amendment. The cost is measurable already (2026-08-22 review): five shapes this hook's scanner blocks pass `commit-bypass` today — `{ git commit --no-verify; }`, `bash -lc '…'`, `timeout 30 git commit …`, `nice git commit …`, `if …; then git commit --no-verify; fi` — and are not back-ported, because a back-port is a fourth divergent copy; they land with the extraction, as do the shared selftest harness (`run`/`expect_*` ×3) and the hand-kept hook roster in `install.sh`, `post-merge`, and `global/README.md`.
- **Revisit the gate** when a push is blocked on a fix-up the user would have waved through more than once a week, or when a review report is found to have been written solely to satisfy the hook.
