# `product-description` admitted as a model-invoked skill, not `onboard-me`'s phase 0

Status: accepted (2026-08-27)

The 2026-08-27 round parked `describe-product` (N1a.53) for want of a second consumer, and the batch plan then resolved that by making the product description phase 0 of `onboard-me`, with a `--describe-only` flag as the door for a BA or PM. Grilling batch 1 before building it overturned both halves, and **Nick decided** to admit the skill and to make it model-invoked — the Team-fit call this record is required to attribute. The suite admits **`product-description`**, a **model-invoked** skill that writes the outside-in behavior record of a product — what its user sees, what they can do, and exactly what happens when they act, including when they abandon halfway — drafted from the code and its tests, then verified against the running product. `onboard-me` does not contain it. It is an opt-in skill under [ADR-0114](0114-opt-in-skills-install-per-repo-from-a-shared-skills-line.md), installed only in a repo whose `CLAUDE.md` lists it on its `Shared skills:` line, and it stays model-invoked there.

The forcing argument is the invocation axis itself. A user-invoked skill is reachable only by a human typing its name, so "`onboard-me` points at it" was never capable of being the second consumer the Extraction test was asking for: a pointer out of a user-invoked skill is a suggestion to a person, not a call. Model-invocation is what actually creates the consumers. `rebuild-contract` ([ADR-0069](0069-rebuild-contract-pre-rewrite-contract-in-repo.md)) declares `requires: product-description` and calls it with `--seed` where the repo has none, and a BA or PM asking how the product behaves reaches it without knowing a command exists — which is what `--describe-only` was trying to buy, at the cost of a flag on a skill that person would never have typed in the first place.

The boundary between this skill and `onboard-me` is **subject, not role**: `onboard-me` maps the inside, how the system is built; `product-description` records the outside, how the product behaves for the person using it. It is not engineers versus product people. `rebuild-contract`'s consumer is an engineer handed an inherited system who needs the outside view before touching the inside, and writing this skill's description with product-manager triggers would hide it from its strongest user. Under the [Team-fit test](0063-team-fit-test-replaces-retire-on-zero-window.md) the moments are two and the roles differ: a BA or PM asked what happens when a member abandons a form halfway, with no document that answers; an engineer starting a rewrite who needs the behavior pinned before the code moves. A new engineer's KT session is not one of them: `onboard-me` reads a description that already exists as evidence, and neither declares nor calls this skill.

The artifact is a document set on one shared eight-section skeleton under `docs/product-description/`, one document per feature area grouped by how the user meets it, with a coverage index derived from the directory: one row per document on disk, `drafted` or `verified` read from each document's footer, and unwritten areas kept in a separate planned-areas list. A stored three-state index lost because every partial build broke its own one-row-per-document invariant. One skeleton for every document is the whole mechanism: gaps show by comparison rather than by inspection. Three parts of the source method were deliberately dropped. There is no `goal.md`, because the skeleton and the index already carry what a standing drafting prompt held. There is no `glossary.md`, because the repo's `DOMAIN.md` owns the vocabulary and a second glossary is exactly the split a domain model exists to prevent. There is no separate `git init`, because the description belongs in the repo it describes. A caller bounds the build with an argument, `--seed`, which writes the foundations and the pilot and leaves every other area on the planned list, so a delegated call never silently commits the caller to a full document set. The bound is an argument rather than an inference about who called, because "another skill delegated this" is agent state, which `writing-for-agents` forbids as a conditional's predicate. The seed includes the pilot because every later document copies it. The skill confirms before its first write into the repo; model-invocation bought reachability, and an unasked directory in someone else's repo was not part of it.

The name is `product-description`, after the artifact rather than the act. `product-behavior` lost to `DOMAIN.md`'s ban on "behavior" as a skill-kind name; `describe-product`, the ledger's sketch, lost because the skill is reached by a model matching a question about behavior, not by a human choosing a verb.

This skill owns the **interrupt taxonomy** — the five families of what can happen mid-interaction: the user's explicit abort, the user doing something else part-way, the environment failing, something else changing the target, and the input channel changing. `work-item-shape` takes one clause and no more, that an interrupted path is an acceptance criterion, which is what N1a.54 asked for in its own closing words. The taxonomy has one home so that the same rows appear in the same order in every document, which is the property that makes a missing row visible. What this record settles is where the taxonomy lives.

Verification against the running product stays in this skill rather than folding into `validate-behavior`. That skill's discipline requires a checker that shares none of the writing session's context, and a model-invoked skill loads into exactly the session that just read the code to draft the document. The two acts also run in opposite directions: `validate-behavior` writes the contract first and a failure indicts the product, while a verification pass writes the document first, from code, and a failure indicts the document or routes to `bug-triage.md`. The shared PASS/FAIL/BLOCKED vocabulary and the build-must-match-the-commit rule are the only real duplication, and they are small enough to leave.

Both halves of the skill were measured before it landed. **The description was probed twelve times** — six messages, each run once on `claude-sonnet-4-6` and once on `claude-fable-5` through `claude -p`, each given only the roster of the repo's 22 model-invoked descriptions and one colleague's message, and asked which it would load and why. Four fired on both models: a BA who cannot find out what happens when a customer closes the tab mid-flow and wants it written down; a port that needs current behavior pinned before the code moves; a direct request for a product description; and an onboarding with nothing written down about what the app does for the member. The onboarding probe measured the description's trigger on a person's message; it does not make `onboard-me` a caller. Only the third contains the skill's name or its distinctive phrases, so the other three are trigger matches rather than string hits. Two controls stayed quiet on both: a bug report (an enrollment form losing input when the network drops) went to `diagnosing-bugs`, and a "decide what it should do after three failed payments" went to `work-item-shape`. **Both anti-triggers were quoted back.** On the bug report Fable named the pull and refused it, writing that the description "is close (it names \"loses the network mid-action\"), but its own description excludes a single behavior question answered directly, and the ask is a diagnosis, not a behavior record" — which is the over-firing risk this record's anti-trigger was written against, caught by that clause. The phrase inside Fable's answer is Fable's own compression of "loses the network, or is interrupted mid-action" and is not a substring of the description; it is quoted here because it is what the model wrote, not as the skill's wording. All twelve probes ran against the final wording: the roster handed to them is byte-identical to the description as it shipped. The BA probe firing on both models is the result that matters: it is the door model-invocation was chosen to open, and the argument against `--describe-only` depends on it.

**The resume seam was run as a wind tunnel** on a small internal service, since the coverage index is what a half-built document set remembers. One agent settled the four axes, wrote the pilot and one foundation, and stopped mid-set; a second, with no shared context and told only to pick up where the first left off, chose the next document from the index and the ownership table, and reproduced the set's shape exactly. Checked mechanically across all three documents rather than from the agent's report: the same eight sections in the same order, the same five interrupt rows in the same order, and the same seven cross-cutting headings in the same order. It updated the index row, the in-progress marker, and the back-reference in the earlier foundation, and it left every document `drafted` — it also found a real defect in the fixture that the fixture's only test would not have caught. That run predates the derived index, so the seam was run again on 2026-08-29 against it. A drifted set was planted: a document on disk with no row and a footer claiming verification, a `verified` row for a file that never existed, and a planned-areas entry for an area already written. A fresh session holding only the body and the disk caught all three, rebuilt the table by listing the directory and reading each footer, and stripped the false `Verified against` line because nothing in that repo can be run. The result was 3 rows for the 3 documents present, all `drafted`. The `--seed` call that ADR-0069's wind tunnel triggered the same day produced the same invariant from the delegated path. The four axes surviving a context boundary is the property the whole artifact rests on, because a resumed session that re-derives them differently produces documents that are each fine and a set that compares to nothing.

## Consequences

- `doc-claims` gains the running product as a named source: a claim in a product description is checkable against observed behavior, not only against code. Triage of what that check finds stays `to-bug`'s; `doc-claims` still renders verdicts and never files.
- The skill's description carries an anti-trigger, so "document how this behaves" in passing does not fire a document-set build.
- `onboard-me` ([ADR-0064](0064-onboard-me-read-only-kt-session.md)) has no `--describe-only` mode and reads an existing description as evidence; it neither declares nor calls this skill. `rebuild-contract` is the only declared caller in the tree.
- `DOMAIN.md`'s Extraction test reads "second consumer" as something that calls rather than points, which is this record's forcing argument stated as the rule.
- `write-skill`'s **Skill-surface security review** runs on this skill: it reads a repo it does not know and writes files into it.

## Deferred

- Whether a repo with no `DOMAIN.md` should be told to build one first or allowed a local terms section. Settled by the first such repo.
- The `verified` bar has not been under real pressure. Neither wind-tunnel agent had a running instance, so marking a document `verified` was impossible rather than merely unearned; what was shown is that the bar holds when verification cannot happen, and against an inherited `verified` claim written by someone else, not that it holds when it is only inconvenient. Settled by a run against a product that can actually be brought up.
