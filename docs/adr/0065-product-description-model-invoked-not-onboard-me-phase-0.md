# `product-description` admitted as a model-invoked skill, not `onboard-me`'s phase 0

Status: accepted (2026-08-27)

> **Amended by [ADR-0069](0069-rebuild-contract-pre-rewrite-contract-in-repo.md):** the second declared caller landed, under the name `rebuild-contract` rather than `rebuild-me`. The revisit trigger below is closed and the "only declared caller" line is superseded.

The 2026-08-27 round parked `describe-product` (N1a.53) for want of a second consumer, and the batch plan then resolved that by making the product description phase 0 of `onboard-me`, with a `--describe-only` flag as the door for a BA or PM. Grilling batch 1 before building it overturned both halves, and **Nick decided** to admit the skill and to make it model-invoked — the Team-fit call this record is required to attribute. The suite admits **`product-description`**, a **model-invoked** skill that writes the outside-in behavior record of a product — what its user sees, what they can do, and exactly what happens when they act, including when they abandon halfway — drafted from the code and its tests, then verified against the running product. `onboard-me` no longer contains it; it declares it.

The forcing argument is the invocation axis itself. A user-invoked skill is reachable only by a human typing its name, so "`onboard-me` points at it" was never capable of being the second consumer the Extraction test was asking for: a pointer out of a user-invoked skill is a suggestion to a person, not a call. Model-invocation is what actually creates the consumers. `onboard-me` declares `requires: product-description` and calls it where the repo has no description, `rebuild-me` will do the same when it lands later in this round, and a BA or PM asking how the product behaves reaches it without knowing a command exists — which is what `--describe-only` was trying to buy, at the cost of a flag on a skill that person would never have typed in the first place.

The boundary between this skill and `onboard-me` is **subject, not role**: `onboard-me` maps the inside, how the system is built; `product-description` records the outside, how the product behaves for the person using it. It is not engineers versus product people. `rebuild-me`'s consumer is an engineer handed an inherited system who needs the outside view before touching the inside, and writing this skill's description with product-manager triggers would hide it from its strongest user. Under the [Team-fit test](0063-team-fit-test-replaces-retire-on-zero-window.md) the moments are three and the roles differ: a BA or PM asked what happens when a member abandons a form halfway, with no document that answers; an engineer starting a rewrite who needs the behavior pinned before the code moves; a new engineer's KT session against a repo that has never described what it does for its user.

The artifact is a document set on one shared eight-section skeleton under `docs/product-description/`, one document per feature area grouped by how the user meets it, with a coverage index marking each `not started`, `drafted` or `verified` (superseded — see Amendments). One skeleton for every document is the whole mechanism: gaps show by comparison rather than by inspection. Three parts of the source method were deliberately dropped. There is no `goal.md`, because the skeleton and the index already carry what a standing drafting prompt held. There is no `glossary.md`, because the repo's `DOMAIN.md` owns the vocabulary and a second glossary is exactly the split a domain model exists to prevent. There is no separate `git init`, because the description belongs in the repo it describes. When a delegating skill calls it, it goes to foundations depth and leaves the rest of the index `not started`, so a delegated call never silently commits the caller to a full document set (superseded — see Amendments: the bound is the `--seed` argument and the seed includes the pilot).

The name is `product-description`, after the artifact rather than the act. `product-behavior` lost to `DOMAIN.md`'s ban on "behavior" as a skill-kind name; `describe-product`, the ledger's sketch, lost because the skill is reached by a model matching a question about behavior, not by a human choosing a verb.

This skill owns the **interrupt taxonomy** — the five families of what can happen mid-interaction: the user's explicit abort, the user doing something else part-way, the environment failing, something else changing the target, and the input channel changing. `work-item-shape` takes one clause and no more, that an interrupted path is an acceptance criterion, which is what N1a.54 asked for in its own closing words. The taxonomy has one home so that the same rows appear in the same order in every document, which is the property that makes a missing row visible. That clause lands with the rest of N1a.54's batch, not with this skill; what this record settles is where the taxonomy lives.

Both halves of the skill were measured before it landed. **The description was probed twelve times** — six messages, each run once on `claude-sonnet-4-6` and once on `claude-fable-5` through `claude -p`, each given only the roster of the repo's 22 model-invoked descriptions and one colleague's message, and asked which it would load and why. Four fired on both models: a BA who cannot find out what happens when a customer closes the tab mid-flow and wants it written down; a port that needs current behavior pinned before the code moves; a direct request for a product description; and an onboarding with nothing written down about what the app does for the member. Only the third contains the skill's name or its distinctive phrases, so the other three are trigger matches rather than string hits. Two controls stayed quiet on both: a bug report (an enrollment form losing input when the network drops) went to `diagnosing-bugs`, and a "decide what it should do after three failed payments" went to `work-item-shape`. **Both anti-triggers were quoted back.** On the bug report Fable named the pull and refused it, writing that the description "is close (it names \"loses the network mid-action\"), but its own description excludes a single behavior question answered directly, and the ask is a diagnosis, not a behavior record" — which is the over-firing risk this record's anti-trigger was written against, caught by that clause. The phrase inside Fable's answer is Fable's own compression of "loses the network, or is interrupted mid-action" and is not a substring of the description; it is quoted here because it is what the model wrote, not as the skill's wording. All twelve probes ran against the final wording: the roster handed to them is byte-identical to the description as it shipped. The BA probe firing on both models is the result that matters: it is the door model-invocation was chosen to open, and the argument against `--describe-only` depends on it.

**The resume seam was run as a wind tunnel** on a small internal service, since the coverage index is what a half-built document set remembers. One agent settled the four axes, wrote the pilot and one foundation, and stopped mid-set; a second, with no shared context and told only to pick up where the first left off, chose the next document from the index and the ownership table, and reproduced the set's shape exactly. Checked mechanically across all three documents rather than from the agent's report: the same eight sections in the same order, the same five interrupt rows in the same order, and the same seven cross-cutting headings in the same order. It updated the index row, the in-progress marker, and the back-reference in the earlier foundation, and it left every document `drafted` — it also found a real defect in the fixture that the fixture's only test would not have caught. The four axes surviving a context boundary is the property the whole artifact rests on, because a resumed session that re-derives them differently produces documents that are each fine and a set that compares to nothing.

## Consequences

- `doc-claims` gains the running product as a named source: a claim in a product description is checkable against observed behavior, not only against code. Triage of what that check finds stays `to-bug`'s; `doc-claims` still renders verdicts and never files.
- The skill's description carries an anti-trigger, so "document how this behaves" in passing does not fire a document-set build.
- `onboard-me` ([ADR-0064](0064-onboard-me-read-only-kt-session.md)) is written against this record: no `--describe-only` mode, `requires: writing-for-humans, product-description`, and a first phase that delegates rather than inlines. The second caller landed as `rebuild-contract` (renamed from `rebuild-me`; see [ADR-0069](0069-rebuild-contract-pre-rewrite-contract-in-repo.md)) and declares it rather than suggesting a command, so the tree now has two declared callers, `onboard-me` and `rebuild-contract`.
- The 2026-08-27 batch plan's landing order and its row for questions 21–24 are amended on disk; batch 1 is now two authoring sessions in dependency order, `product-description` before `onboard-me`.
- `write-skill` step 5, the security lens, runs on this skill: it reads a repo it does not know and writes files into it.

## Amendments

- **2026-08-27, after review** — Five decisions in this record were reopened by the `/review-changes` pass on the change that implemented it, and settled by Nick in the fix pass. (1) **A delegated call builds the pilot too**, not the foundations alone: this record's own resume-seam evidence ran on a state that included a pilot, and the build order it endorses says every later document copies it, so foundations-only delegation asked for the one artifact the set is built from to be skipped. (2) **The bound is an argument, `--seed`, not an inference about the caller** — "another skill delegated this" is agent state, which `writing-for-agents` forbids as a conditional's predicate, and the caller passed no signal. (3) **The coverage index is derived from the directory**, with `verified` read from each document's footer and unwritten areas kept in a separate planned-areas list; the three-state index made every delegated call violate the skill's own one-row-per-document invariant. The resume seam this record wind-tunnelled has not been re-run against the derived shape — that is now the open item. (4) **The skill confirms before its first repo write.** The invocation-axis argument above is unaffected; what it bought was reachability, and an unasked directory in someone else's repo was not part of it. (5) **The Extraction test's "second consumer" is sharpened in `DOMAIN.md`** to mean something that calls rather than points, which is this record's forcing argument turned into the rule instead of left in the record. The claim of two declared callers is corrected above: `onboard-me` is the only one in the tree.

- **2026-08-27, after review** — The verification-ownership deferral below is **closed against the merge**, and a claim made earlier in the same fix pass is corrected: that pass recorded the blocker on folding verification into `validate-behavior` as the invocation axis plus the linter. That was wrong, and the real reason is stronger. `validate-behavior`'s discipline requires the checker to share none of the writing session's context — its own body says a contaminated run "is not a lower-confidence check; it is not this check at all" — and model-invocation means loading into exactly the session that just read the code to draft the document. The axis is load-bearing for the discipline rather than an accident of classification, so flipping it to make the fold possible would destroy the thing being folded in.

  The two acts also run in opposite directions, which is why the duplication is a rediscovered shape rather than an accident. `validate-behavior` writes the **contract** first — what the product should do, by a non-checker — and a failure indicts the product. A verification pass writes the **document** first — what the product does, drafted from code — and a failure indicts the document, or routes to `bug-triage.md`. A verification pass is by construction a contaminated run by `validate-behavior`'s standard, because the document came from the code. The shared PASS/FAIL/BLOCKED vocabulary and the build-must-match-the-commit rule are the only genuine duplication, and they are small enough to leave.

- The `verified` bar has not been under real pressure. Neither wind-tunnel agent had a running instance, so marking a document `verified` was impossible rather than merely unearned; what was shown is that the bar holds when verification cannot happen, not that it holds when it is only inconvenient. Settled by a run against a product that can actually be brought up.
