# `onboard-me` admitted: a read-only KT session over a repo, delegating the product description

Status: accepted (2026-08-27) — the workspace filenames below were renamed by [ADR-0077](0077-tightening-round-one-house-style.md): `KT-MAP.md` is now `kt.md`, and `teach-me`'s `MISSION.md` is now `mission.md`. The body stays as it landed; read the names through that rename.

The 2026-08-27 round surfaced four knowledge-transfer candidates sharing one shape — `describe-product` (N1a.53), `onboard-me` (N1b.22), `offboard-me` (N1b.25), `rebuild-me` (N1b.28) — every one user-invoked, high-stakes, and parked in the ledger for want of a second consumer. The [Team-fit test](0063-team-fit-test-replaces-retire-on-zero-window.md) admits them on the moment rather than the count. This record covers `onboard-me`, a user-invoked skill that runs a knowledge-transfer session over a repo the person does not know: evidence-tagged findings, an honest map of what is still dark, one rung per turn, and each topic worth going deeper on handed to `/teach-me`. It reads the repo and never changes it.

The moment is a **recurring** one, and the record is written for the recurrence rather than for a date. One engineer joins on 2026-08-31 and three follow; every one of them opens a repo nobody has walked them through, and the fourth needs the skill exactly as much as the first. A record pinned to a single start date expires the week it lands and takes the skill's justification with it. The role is that engineer. What makes the moment costly is that the alternative is a senior engineer's afternoon, repeated per joiner, producing nothing durable.

`onboard-me` is a new skill rather than a fold into `teach-me`, which the ledger named as the first fold target. A KT session and a lesson are different shapes. `teach-me` runs mission intake, then one lesson per sitting against a per-topic workspace; a KT session's product is a *map* — what is lit, what is still dark, and which unknown is worth lighting next. Folding the map into a lesson sequence would make the repo the mission and lose the map, and a learner who cannot yet name a mission for a codebase is precisely the person a lesson cannot serve. The two compose instead: `onboard-me` builds the map and hands each topic it names to `/teach-me`, whose workspace is the learner's durable record. `teach-me` carries the reverse pointer, so a learner who arrives there without a topic is sent here. That composition is also why the KT session writes no `.kt/` trail into the repo as its upstream does — a second trail beside the learning workspace would split the record in two and leave a directory behind in someone else's repo.

The product description is **not** a phase of this skill. [ADR-0065](0065-product-description-model-invoked-not-onboard-me-phase-0.md) admits `product-description` as a model-invoked skill in its own right, and `onboard-me` declares `requires: writing-for-humans, product-description` and delegates to it, only where the repo lacks a description. An earlier draft of this record argued the opposite — that the description failed the Extraction test for want of a second consumer and so had to live here as phase 0, with a `--describe-only` flag as the door for a BA or PM. Grilling batch 1 killed both halves, and **Nick took the call** on both: a user-invoked skill is reachable only by a human typing it, so a pointer from `onboard-me` was never able to be the second consumer the test wanted, and the flag existed only to serve people who would never have typed `/onboard-me`. Making the description model-invoked gives it real callers and a door that does not require knowing a command. **There is no `--describe-only` mode.**

The split between the two is subject, not role: `onboard-me` maps the inside, how the system is built, and `product-description` records the outside, how the product behaves for its user. Both roles need both views at different moments, which is why neither skill is written for a job title.

**Nick decided to admit the skill**, as the Team-fit test requires the record to state; the grill put the counter-case on it. Two alternatives lost. Keeping all four candidates parked until an ask arrives — the round's own recommendation — was rejected once the Team-fit test replaced the count: the moment is named and recurring, and a skill that lands the week after the engineers start is a skill that did not exist when it was needed. Folding into `teach-me` lost for the reason above.

## Consequences

- `rebuild-me` and `offboard-me` follow in the same round under their own records. `rebuild-me` declares `requires: product-description` directly rather than pointing a human at a command, which is what model-invoking the description bought.
- `onboard-me` makes no repo write of its own. The description, when the delegate writes one, lands under `docs/product-description/` on confirmation; the map, the unknowns, and the per-topic records land in the `teach-me` workspace outside the repo.
- `src/teach-me/SKILL.md` gains the disambiguator naming `/onboard-me` for a learner who cannot yet name a mission for a codebase, and the router and README carry both directions.

## Deferred

- Whether the map's evidence tags belong in `teach-me`'s own progress format, so a resumed KT session reads them back without `onboard-me` loaded — settled by the first resumed session that needs them.
- Whether an agent works out from the skill body alone that the map lives outside the repo, or only does so when told. Two controls this round were told by their scenario; neither tested the body on its own. Settled by a control that is not told.

## Amendments

- **2026-08-27, after review** — The `/review-changes` pass on the build found the skill's only durable product had no defined location and a circular dependency on `teach-me` — the workspace needs a mission, the mission comes from the map, the map goes in the workspace — and Nick settled it in the fix pass. The map is `KT-MAP.md` at the top of `<learning root>/<repo-directory-name>/`; the root is the one `teach-me` persists as a user memory, defaulting to `~/learning/`; the workspace is keyed on the repo rather than a topic slug, because a KT session has a repo and not yet a topic; and **no `MISSION.md` is written** — `teach-me` writes one when the learner brings back their first topic. `src/teach-me/SKILL.md`'s workspace tree carries `KT-MAP.md` as a file it reads and never writes. This closes the second half of the revisit trigger below in advance: the map is findable by name from the first run, so a rebuilt-from-scratch map would now be a different failure than the one that trigger anticipated.
- **2026-08-27, after review** — Two further corrections from the same pass. The delegation to `product-description` passes an explicit bound, `--seed`, rather than relying on that skill to infer that it was delegated; the seed is the four axes, one pilot document, the foundations, and a list of unwritten areas ([ADR-0065](0065-product-description-model-invoked-not-onboard-me-phase-0.md)'s amendment carries the reasoning). And the `Launching skill:` load gate on that delegation is removed: `write-skill` reserves the gate for a delegation carrying the caller's whole job, and this record is explicit that the description is optional to the session — the skill now says what to do if the delegate does not load, which is to say so and go on, never to write the description itself.
- **2026-08-27, after review** — The secrets prohibition cut above is **partly reinstated**, on a distinction the original controls did not test. Those controls tested whether an agent would inline live credentials into code; this skill writes no code, and its actual surface is *transcription* — quoting a config value as a `[fact]` into a map that lands outside the repo and outside its `.gitignore`. That failure was never controlled for, so the clean control did not license the cut on this surface. The `[fact]` bullet now carries one clause: cite `file:line` and the kind, never the value. The finding is not a re-litigation of the control result, which stands for the failure it tested.
