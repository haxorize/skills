# Domain — Skills Repo

Ubiquitous-language glossary for the entire skills repo. Covers the areas of work the skill suite supports — shaping backlog work (Feature/Story/Task/Bug publishing), charting foggy efforts (chart-course), architecture review (review-architecture), recording decisions (ADRs), implementation, review, and landing (committing and ship), learning capture and adoption verdicts, tutored learning (teach-me), knowledge transfer over an unfamiliar repo (onboard-me), what a departing engineer knows that the repo does not (offboard-engineer), what a system about to be rewritten must keep (rebuild-contract), a multi-week evaluation's evidence (evaluation-ledger), and the outside-in record of what a product does for its user (product-description) — plus the meta-vocabulary of the skills themselves. It does not carry subject-matter vocabulary: a **Domain skill** defines the terms of its own field in its body (`phi-safe-code`'s *sink*, *allow by name*, *opaque ID*; `health-literacy`'s *member-facing copy*, *the next move*, *required language*; `accessible-ui`'s *success criterion*, *touched*, *exercised*, *evidence*, *ledger*), because each new one would otherwise import a discipline's whole lexicon here. The DOMAIN-conformance lens reads a Domain skill's body for those terms, not this file.

## Skill mechanics

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **Skill** | A Claude-Code-loadable behavior packaged as a directory with a `SKILL.md` root file | Plugin (Claude-Code term, distinct), Macro |
| **`SKILL.md`** | The mandatory root file of a Skill (≤200 lines), carrying YAML frontmatter and imperative-voice instructions | — |
| **Description** | The ≤1024-char frontmatter field the agent reads to decide whether to load a Skill | Summary, Tagline |
| **Frontmatter** | The YAML metadata block at the top of `SKILL.md` (`name:`, `description:`) | Header, Metadata block |
| **Reference file** | A supplementary doc under `references/<name>.md` (≤200 lines each) | Helper file, Sub-doc |
| **Repo-agnostic skill** | A Skill that works in any project without per-repo config | Universal skill, Generic skill |
| **Convention skill** | A project-local, **Model-invoked** Skill encoding the conventions of a specific stack (e.g., a `database` Skill for Alembic patterns); global skills discover and invoke it **by role**, named in CLAUDE.md `## Convention skills` | Stack skill, Project skill |
| **Domain skill** | A **Model-invoked** Skill encoding a subject-matter discipline the default output of the models the invoking teams run gets wrong — accessibility, PHI handling, FHIR interop — rather than a stage of the build flow. Admitted by the **Team-fit test** like any other Skill, and by the **Gap-and-stakes test** on top of it; lives in plain `src/` beside the process skills, a placement that is re-decided when a lint, install, or selftest loop first has to special-case Domain skills — the count alone does not re-open it | Domain pack (a bundle imported wholesale — never admitted as-is), Stack skill (that is a **Convention skill**) |
| **Data-class safe-code skill** | A **Domain skill** governing one class of sensitive data at every *sink* it can leak into (`phi-safe-code` for PHI); each class is a separate skill admitted on its own **Gap-and-stakes test**, and the candidates (`secret-safe-code`, `pii-safe-code`, `pci-safe-code`) stay unadmitted until one clears it — the cut and its re-admission condition are an ADR's to record | Sensitive-data skill (the rejected unified form — one skill for every class), Safe-code pack |
| **Off-path skill** | A **User-invoked** Skill serving the person's judgment, learning, or communication off the build path (`merge-quiz`), distinct from a process skill (a stage of the flow) and a **Domain skill** (subject matter the models the teams run get wrong). Judged by the **Team-fit test** like any other Skill, with two extra admission prongs on top of it: the off-path lens, and a named typist (observed friction is not required). Team-fit governs where they disagree, and it alone decides retention | Productivity skill, Personal skill, Soft skill |
| **Deprecation stub** | A retired skill name kept in `src/` for one retire-on-zero window after a rename or merge, its body one line telling the human which name to type instead (`grill-and-record` → `grill-me`, retired 2026-08-26 on a zero window; a user-invoked target is a human suggestion, so the stub cannot load it); earned only by typed muscle memory — a name no transcript typed gets no stub, and a name with typed history earns one unless the decision to skip it is recorded against this row (the 2026-08-30 renames were waived that way; ADR-0057's amendment of that date carries the counts and the reason) | Alias skill, Redirect |
| **Retire-on-zero window** | The retirement test a **Deprecation stub** alone carries: one window after the stub lands, zero typed invocations on the machines its typist works from retires it, and any typing extends it one more window. A stub serves one person's muscle memory, so that person's history is the whole population. A **Skill** never carries the window: the population it serves includes teammates whose sessions nobody measures, so a zero on any one machine is load evidence, not a verdict — the **Team-fit test** judges skills | Usage window, Sunset period, Grace period, Retire check (on a skill — that is the **Team-fit test**) |
| **Team-fit test** | The admission-and-retention test for a **Skill**, both halves required: it is admitted or kept when its deciding record names a concrete moment in a product engineering team's work and the role who hits it — a BA drafting a story, an engineer handed a rewrite, a lead losing an engineer — and it is retired when an existing Skill or global rule already serves that moment (the pruning test applied to a whole skill). Fire counts on any machine are evidence for the case, never the verdict; the call is the team lead's, stated in the record. How the check runs — the stocktake, the verdict per skill, the stub window — is `audit-skills`': its Keep names the moment and the role, its Overlap lens is the covered-by half (a global rule counts), and its Usage read takes the counts from `scripts/skill-usage.sh`, never from recall. Every **Skill** takes this test, a **Domain skill** included; the **Gap-and-stakes test** is the extra admission bar a Domain skill clears on top of it, and Team-fit is what retains one | Usefulness (unscoped), Usage-based retirement (the count form this replaces), Fire count (evidence, not the test) |
| **Gap-and-stakes test** | The extra admission bar a **Domain skill** clears on top of the **Team-fit test** every Skill takes, all three prongs required: the default output of the models the invoking teams run — not the authoring session's model — is reliably wrong or incomplete in the domain (not merely unstyled), the failure is costly at the organisation (regulatory, member-harm, audit), and more than one team would invoke it. A source failing any prong is mined for portable ideas and the pack rejected | Regulated-surface test (the narrower rejected form — a named regulation satisfies the stakes prong but is not required for it), Usefulness (unscoped) |
| **Hoist** | The act of making a Repo-agnostic skill globally available by symlinking it into `~/.claude/skills/` | Promote (different stage), Install |
| **Usage read** | A per-skill reading of typed `/name` invocations and model `Skill` loads over a window, taken from one run of `scripts/skill-usage.sh` on the machine the read runs on — never recalled, never grepped by hand. `audit-skills`' fifth dimension, and the figure a `mine-skills` row's `usage` cell states. A figure carrying `+` is a floor, not a total. Evidence for the **Team-fit test**; the count alone decides only a **Deprecation stub** | Fire count (the figure, not the read), Load count (same — the read is the canonical act), Usage stats, Telemetry |
| **Failure-driven escalation** | The `write-skill` wording rule: judgment-framing is the default; a hard prohibition (paired with a rationalization table and red-flags list) is reserved for a rule the agent demonstrably skips under pressure | Blanket caps ban (the prior rule), Authority-by-default |
| **Form-to-failure table** | The authoring decision table mapping a skill's observed failure type to the wording form that fixes it; the table lives in `writing-for-agents`' `predictability.md`, the single source of truth | — |
| **Micro-test** | The cheap wording check run while authoring a discipline skill: execute the pressure scenario *without* the skill as a control (no control failure → nothing to fix), then 5+ fresh-context reps with the wording; high variance across reps is itself the failure signal | A/B test (broader), Eval (overloaded) |
| **No-op rule** | A skill instruction whose removal changes nothing — a fresh-context agent behaves identically without it; review judgment only *nominates* one, and only a Micro-test control run confirms it before deletion | Filler (a prose-clarity defect, different failure), Dead rule (implies never reached — a no-op fires and still changes nothing) |
| **Control-clean rule** | A skill rule whose **Micro-test** control rep produced no failure to fix, kept anyway on a ground its record states — the named case being a fixture or harness that supplies what the rule supplies, so the clean control is evidence about the harness, not the rule — and marked untested rather than proven. The exception's form and fence live in `write-skill`'s `testing-skills.md`, beside its opposite — a control whose transcript names the skill under test is a leaked control, invalidated and re-run, never kept under this rule; ADR-0069/0070/0071/0072 are the records that argued it | Control-passed (a control that found no failure proved nothing), Clean rule |
| **Wind tunnel** | The simulated-use check answering what a skill is like to *wield*, as against whether its wording binds (**Micro-test**) or its description loads (**Trigger test**): a quarantined wielder role-plays scenarios and the transcript is judged rather than the prose. Offered for skills that hold a conversation or keep an artifact, never a required gate. The scenario roster, the quarantine mechanism, and the judging criteria live in `write-skill`'s `testing-skills.md`, the single source of truth | Simulation (unscoped), Eval (overloaded — see **Micro-test**) |
| **Load suppression** | The disclosure failure `writing-for-agents` names: a block every run executes, pushed behind a pointer to a reference file, loses to the pointer's own summary of it — the agent reads the paraphrase, finds it workable, never opens the file, and the rule runs as a paraphrase. The mirror of the rule-placement failure, which is a conditionally-loaded file holding a rule about a branch not running. The remedy lives in `writing-for-agents`, the single source of truth | **Lazy load** (a deliberate invocation tier — unrelated), Skipped reference |
| **Trigger test** | The description check for a Model-invoked skill that misfires or fails to fire: a handful of realistic should-trigger prompts plus near-miss should-not-trigger negatives, run in fresh contexts — the near-misses carry the signal; fixed by sharpening triggers, never by enumerating queries | Trigger eval (the official heavyweight form — 20 queries, train/test splits) |
| **Undertriggering** | The default description failure mode: the model handles a query itself rather than loading the applicable skill — what trigger-rich, front-loaded descriptions fight | — |

## Skill modes & shared concepts

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **Synthesis-only** | A Skill mode that drafts from existing conversation context without interviewing | — |
| **Grilling session** | An interactive interview that stress-tests a plan | Interview, Q&A |
| **False yes** | A non-answer confirmation closing a Grilling session — "sounds good", "whatever you think", "I guess" — that hands the decision back to the agent; recovered by diagnosing the kind: *hasn't-decided* gets re-asked with two concrete options, *can't-evaluate* (repeated deferrals on questions needing domain judgment) gets a **Decision map** first | Soft approval, Hedged yes |
| **Dwell** | `grilling`'s move on a weak-but-real answer ("should be fine", "probably", "we'll figure that out later"): staying on the point as an announced move rather than a silent re-ask, held for as many rounds as sharpening needs. Distinct from the **False yes**, which is a non-answer rather than a weak one. How the move is conducted lives in `grilling`, the single source of truth | Follow-up question (ordinary probing — a dwell is announced and holds position), Pushback (vague) |
| **Craft gate** | The `grilling` rule deciding who wins a disagreement, split by kind of content: **user-owned** content (their beliefs, their decisions) is recorded as the user states it once real pressure has been applied, while **craft-gated** content — anything carrying objective quality criteria, such as a leading question or an unsettleable acceptance criterion — does not bend, however the user insists. What the refusal covers and what it spares lives in `grilling`, the single source of truth | Veto (implies refusing the person), House style (a preference, not a criterion) |
| **Decision map** | `grilling`'s response to a can't-evaluate deferral: 3–7 items, each a decision in the territory the user can't weigh — what it is in their vocabulary, why it matters for this plan, the realistic options, a recommended default; unpicked items take the default, recorded as an explicit assumption. An undecided expert never gets one — options, not teaching | Blindspot pass (upstream CE name), Teaching pass (implies tutorial) |
| **Predictable-answer gate** | `grilling`'s per-question filter: a question whose answer is already predictable from what the user said is not asked — the assumption is stated in the round's preamble and the question is spent on a branch that is open. The grill's half of the recommend-and-proceed bins: facts are run, judgments stated, only decisions reach the round | Obvious-question filter, Skip rule |
| **Pre-mortem** | The grilling closing question — "it's a year from now and this flopped; what went wrong?" — asked before declaring the decision tree resolved, to surface branches the tree missed | Retrospective (backward-looking, different artifact) |
| **Closure sweep** | The grilling pass run before the Pre-mortem: walk the standing categories the decision tree may never have grown (functional scope, data model, interaction, non-functionals, integrations, edge cases, terminology, completion signals) — each is settled, a missed branch to grill, or deliberately out: dismissed with a stated reason or deferred visibly; silence is not a state | Completeness check (vague), Checklist pass (implies mechanical) |
| **Must-NOT probe** | The grilling question asked at least once, after the wants are mapped: "what could this plan silently become that you would *not* want, but nothing said so far forbids?" — over-generate, keep only violations of values or intent; routine engineering risk belongs to the Pre-mortem | Inversion (the `diverging` move — generates framings, not prohibitions) |
| **Fixation** | Attention concentrated on the current problem frame so new output becomes local variations of it — the trigger for `diverging`; the trigger is fixation signals (iterations circling one idea, a binary with two bad options), never stakes | Local optimum (different mechanism), Tunnel vision (informal) |
| **Fire test** | `diverging`'s per-move check: could this output have been produced without the move? If yes the move didn't fire — commit harder or re-diagnose the stuck-pattern; re-diagnosis after a miss is not menu-rotation | — |
| **Behavior contract** | The pre-run specification `validate-behavior` validates against — user tasks, expected observable behavior, Anti-cheat probes, required evidence — written *before* the checker touches the target, so it states what the target should do, never what the checker observed it doing; for legacy behavior with no request text, a non-checker derives it from code and a human validates it before use | Test plan (broader), Spec (overloaded), **Rebuild contract** (pre-rewrite, holds everything that must survive a reimplementation, derived from the source on purpose) |
| **Anti-cheat probe** | A `validate-behavior` move that distinguishes real work from displayed success — varied input the output must follow, persistence across refresh, invalid-input handling, and confirmation that buttons and commands do real work rather than only displaying success text; the probes are themselves suspects — force one to fail before trusting an all-PASS run | Smoke test (different purpose), Sanity check (vague) |
| **Negative-space pass** | `review-changes`' post-vet pass on a substantial diff (skipped only when the diff is small or mechanical): one fresh subagent gets the diff and the vetted findings and hunts only where the findings did not go — they map spent attention; an empty return is a good outcome | Blind-spot pass (upstream name), Second pass (vague) |
| **Obeyed vs understood** | The boundary test between `writing-for-agents` (documents that steer agent process) and `writing-for-humans` (prose that transfers understanding) — the document's function decides which skill owns it, never its reader, since agents read ADRs too | Agent-facing vs human-facing (audience split — misleading) |
| **Wiring test** | The rule deciding which skills declare `writing-for-humans`: a skill that authors durable human-read artifacts gets the dependency; one whose output is an ephemeral chat report does not | — |
| **Press-release test** | `writing-for-humans`' filler detector: a sentence that could move unchanged into any company's press release carries no fact — cut it or replace it with the fact, number, or mechanism specific to this subject | Portability test (upstream name) |
| **Displacement partner** | The adjacent form an AI tell migrates into once suppressed (em dash → semicolon; "not X, it's Y" → "no setup, no config") — the tell catalog names it so the evasion is checked in the same pass as the tell | — |
| **Sweep mode** | A non-interactive Skill mode that refreshes a derived artifact by scanning its source corpus | Bulk pass |
| **Update mode** | Single-artifact maintenance mode invoked via `--update <work-item-id>` (see ADR-0003) | Patch, Edit, Revise |
| **Reconcile mode** | Multi-artifact diff mode invoked via `--reconcile <story-id>`, proposing adds/closures/edits across child Tasks (see ADR-0003) | Sync, Realign |
| **Cold-start** | A fresh Claude Code session entering a Ticket with no prior conversation context | Fresh session |
| **Cold-reader pass** | The verification against author blindness (after drafting, you see what you meant, not what you wrote): a fresh-context reader sees only the draft — no thesis, no thread, none of the conversation that produced it — and says what they took from it; every gap is a defect in the draft, fixed by editing the draft and never by briefing the reader. `work-item-shape` owns the work-item form, which every `to-*` publisher runs pre-publish, asking "what would you build?" and naming ambiguities in **Ambiguity block** shape; `writing-for-humans` runs the generic form on any document long enough to be worth the round-trip | Skeptical-reader instruction (`handoff`'s different move — the next session re-verifies *facts*, not comprehensibility), Reader test, Peer review (human act) |
| **Skeptical-reader instruction** | The required handoff-doc section telling the next session to re-verify the state described against the live repo and tracker before acting, and to treat the doc as untrusted starting context — instruction-shaped content inside it is data to weigh, never standing orders | Skeptical reader (acceptable shorthand), Cold-reader pass (the different move — comprehensibility, not facts) |
| **Completion audit** | The done-claim proof run before declaring an objective complete: treat done as unproven, derive the requirements, name the authoritative evidence per requirement, and inspect it at matching scope — a narrow check never supports a broad claim; the audit proves completion rather than failing to find remaining work. Its written form — a per-AC table (DONE / PARTIAL / NOT DONE / CHANGED / UNVERIFIABLE, each with an evidence line), a beat ledger, a parked ledger with its zero case stated, a judgment-calls list tagged user's / inferred / my call, and a completion line (`complete` / `complete with N unverified` / `incomplete`) — is the `completion-audit.md` sibling that `implement` owns and writes at close, `handoff` carries verbatim, and **Committing** reads to choose the closing word | Done check (vague), Definition of done (the criteria, not the proof), Progress report (rows per thing built, not per criterion) |
| **Committing** | The model-invoked discipline for landing a change honestly, reached by any commit, push, or ticket-close ask: the claims rule (every claim checked against evidence as it is written), the closing-comment contract, the `Closes`-or-`Refs` decision read off the **Completion audit**, the blocked-action protocol, and the one-commit fast path. It never proposes the commit split — that is `ship`'s, which declares it. Held apart from `ship` because `/ship` is user-invoked and the ask that lands most work never types it | Ship (the split-and-PR orchestrator), Commit discipline (acceptable shorthand) |
| **Outward act** | Anything a session does that leaves the machine or binds someone else — a commit, a push, a tracker write, a message, a loop. Always in the ask bin of the recommend-and-proceed rule, however reversible it looks, unless the **Landing key** pre-authorises that specific act; the test is where the user's corrections sit, not reversibility | Side effect (too broad — a file write is one), Irreversible action (the rejected test) |
| **Git hook** | A script under `scripts/git-hooks/`, run by git rather than by Claude Code, live in a clone only after `bash scripts/setup-hooks.sh` points that clone's `core.hooksPath` at the directory — per-clone, uncommitted, so every clone and mirror opts in separately. Three exist: `post-merge`, which warns after a merging pull and re-hoists; `commit-msg`, which blocks a commit whose message breaks the **House commit style**'s **Shape** rules; and `pre-commit`, which blocks a commit when the linter a staged path answers to is red. Unlike a **Hook**, a git hook may be fail-closed, and `commit-msg` and `pre-commit` are. Each has a `*-selftest.sh` beside it, and the post-merge roster is derived from that, never hand-kept | Hook (the PreToolUse mechanism — a different thing; `pre-commit` is a git hook, not a **Hook**), Pre-commit hook (bare, as if it were the only kind — name the hook, `pre-commit`) |
| **Landing key** | The `Landing:` block in a repo's `CLAUDE.md`, read by **Committing** and `ship` before any **Outward act**, by `implement` and `diagnosing-bugs` for its defect policy, by `handoff` for its Next-steps rule, and from disk by the `review-receipt` **Hook** for `Review required:`: branch policy, whether a PR is required, whether push and ticket-close are pre-authorised, whether a push needs a **Review receipt** (`Review required:`, absent means `no`), and the defect policy (default "fix, don't file" — filing is the user's ask: `to-bug` for a defect, `to-tasks` or `to-story` otherwise). Sibling of the `Issue tracker:` block; no block means nothing is pre-authorised. It governs the *authorisation* to land, not the *shape* of what lands: a `commit-msg` **Git hook** gates every commit in an opted-in clone unconditionally, with no key to relax it | Ship config, Branch policy (one of its lines) |
| **Registry block** | The `## Registry` section of a repo's `CLAUDE.md`, written by `onboard-repo` and read by `upgrade-deps`: `Minimum release age:` and any other curation line a package proxy enforces. The number is the org's and lives only here, never in a skill. Sibling of the **Landing key** and the `Issue tracker:` block | Proxy config (the proxy's own file, not this block), Curation policy (the org's rule, which the block records) |
| **Global rule** | A rule file under `global/rules/`, symlinked into `~/.claude/rules/` by `install.sh` so it holds on every turn with no skill loaded — the rung for a rule that kept failing as skill or memory prose. Admission: a skill must depend on it (named in its `Depends:` line and citing it — lint checks both) and its `Why not a hook or lint:` line carries the **Count-based control** — a count over a stated window of the artifacts the rule governs, not a judgment that prose should hold; five exist (evidence, recommend-and-proceed, no-unasked-commits, large-write-chunking, outbound-dash-sweep) | Global CLAUDE.md line (hand-kept, unversioned), Hook (the mechanical rung — a Global rule is for what a hook cannot see) |
| **Count-based control** | The measurement that decides a **Global rule**'s `Why not a hook or lint:` line: over the artifacts the rule governs in a stated window of at least 30 days, how many a mechanism would have fired on and how many of those were the failure, on the line with the window and the corpus, so a rule held by prose alone is caught dying by the history it was meant to shape. It decides one rung — whether a rule stays prose in `global/`; `predictability.md`'s *control run* (the **Micro-test**'s control arm) decides whether a skill's prose rule binds at all. ADR-0075 gave it its one home, and its batch-4 amendment carries the five counts | Control (bare — see § Flagged ambiguities), Control run (the micro-test's arm), Usage count (`skill-usage.sh`'s figure, a different measurement) |
| **Hook** | A script under `global/hooks/` whose header carries an `# Install note:` line — the roster `install.sh` and the post-merge hook read — that the user wires into `~/.claude/settings.json` as a `PreToolUse` check, for the class of failure a mechanism can see before a tool call runs: a command-line shape (`rename-safety`, `commit-bypass`) or a precondition on disk (`review-receipt`). Always fail-open — its own errors allow with a stderr breadcrumb; each ships with a `*-selftest.sh` expect/reject table. Its header carries a `Depends:` line naming the skill it is the mechanical half of, which lint does not check — the **Global rule** `Depends:` is the checked one. The directory also holds the **Hook library**. Distinct from a **Git hook**, which git runs | Gate (the act, not the script), Guard, Git hook (a different mechanism — see its own row) |
| **Hook library** | `hook-lib.sh` / `hook-lib.py` (the payload parse, the command-line scanner, and the fail-open rule every hook inherits — the lib's header is that part of each hook's contract) and `selftest-lib.sh` (the expect/reject helpers every selftest shares — two files, `global/hooks/selftest-lib.sh` for the hook selftests and `scripts/selftest-lib.sh` for the gate selftests, diverged by design per `scripts/README.md`), beside the hooks under `global/hooks/` but not hooks: no `# Install note:` line, never wired, never run on their own | Shared hook, Common hook, Helper script |
| **UNVERIFIED / UNVERIFIABLE** | Two markers, not one. `UNVERIFIED:` (the global evidence rule) prefixes a claim stated without re-checking it in this message — the fix is to check — and, on a deferral, one whose durable record does not exist yet — the fix is to write it. `UNVERIFIABLE` (the **Completion audit**, **Committing**, and the global evidence rule) is a status for evidence that cannot be obtained from here — a system outside the repo, a capture that never landed — and its line names what would prove it; the fix is to say so, never to launder it into a pass | Unverified (bare — which marker?), Unknown, Skipped |
| **Cold-start loader** | A Skill that fetches a published Ticket — body, relations, and comments — back into the conversation as implementation context; embodied by `from-ticket` | Loader (when used alone), from-work-item (earlier name) |
| **Design-record comment** | A ticket comment carrying design context the published body deliberately omits — an interface sketch, rejected shapes, a grill decision, typically fenced code plus rationale; written as a fallback when no ADR records the design, surfaced in full by the Cold-start loader | Design comment (unscoped), Comment (bare — most comments are status chatter, not design records) |

## Skill invocation

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **Invocation** | The axis that splits every Skill by *who can reach it* — the human only, or the model too | Triggering, Activation |
| **User-invoked skill** | A Skill reachable **only by a human typing its name**; carries `disable-model-invocation: true`, which hides its `description` from the model. The description is **human-facing** (a one-line summary, no trigger list). Its job is to **orchestrate**. | Manual skill, Human-only skill |
| **Model-invoked skill** | A Skill reachable by **model or user** (the default — omit `disable-model-invocation`). The `description` is **model-facing** and keeps rich trigger phrasing so auto-invocation fires. Holds reusable discipline. | Auto skill, Agent skill |
| **Orchestrator skill** | A (typically User-invoked) Skill — `grill-me`, `sweep-domain`, `review-architecture` — that drives a workflow end-to-end and delegates reusable discipline to Discipline skills | Wrapper, Entry skill |
| **Repo-local skill** | A Skill under this repo's own `.claude/skills/` (`mine-skills`, `sweep-corpus`) that acts on this repo alone and is never hoisted into `~/.claude/skills/`: it may name this repo's paths and procedure, `scripts/lint-skills.sh` reads it for the slash-form sweep and the evaluation-ledger vocabulary check only — its frontmatter, size and reference-link passes skip it — and the router does not route to it. Neither a Convention skill (those belong to a target project) nor a Repo-agnostic skill | Project skill (clashes with Convention skill), Private skill |
| **Discipline skill** | A Model-invoked Skill holding a reusable discipline the model can reach for autonomously (`grilling`, `domain-modeling`, `codebase-design`) | Behavior skill (the earlier term — clashes with **Behavior contract**), behavior (bare, as a skill kind — "the `X` behavior"), Helper skill |
| **Declared dependency** | A Discipline skill another skill names in its `requires:` line — an Orchestrator declares the Discipline skills it delegates to, and a Discipline skill may declare one it **Lazy load**s; `scripts/install.sh` resolves it so the Prose invocation always finds it. Relaxes ADR-0007 atomicity from "lone skill" to "skill + its declared deps" | Skill import, Require |
| **Skill tool** | Claude Code's own tool for loading a Skill by name — the runtime that a **Prose invocation** resolves to. Distinct from a **Skill**, which is the directory it loads; naming it in a body is what the model acts on, not a hard include (see the **Load-bearing delegation** row) | Skill loader, Skill call |
| **Invocation form** | Which of the three surface forms a reference takes — ``Call the Skill tool with `<name>` `` where the **model** fires it, `/<name>` where a **human types the command**, a plain backtick where nothing fires. Orthogonal to the **Load gate**; the decision procedure and worked examples live in `write-skill`, this file owns which form means what | Reference form (a fourth "Reference X" — clashes with **Reference file**), Slash form (names one of the three) |
| **Prose invocation** | The soft, Claude-mediated mechanism by which one Skill instructs Claude to run another (``Call the Skill tool with `grilling` ``). There is no hard cross-skill include; it works only if the target is a Model-invoked skill **and** installed. Splits by what a silent miss costs into four tiers — **Load-bearing delegation**, **Ungated soft delegation**, **Lazy load**, **Opportunistic reference** | Cross-skill call, Skill reference (clashes with Reference file) |
| **Load-bearing delegation** | A **Prose invocation** whose target carries the invoking skill's *method*: strip the target and the caller has no procedure left, so a silent non-load makes it emit the wrong **kind** of artifact rather than a worse one (`grill-me` → `grilling`, `implement` → `tdd`, `ship` → `committing`). Judged on that consequence, by the necessity procedure `write-skill` owns — the definition does not name where the delegation sits, because a placement in the definition makes the **Load gate** test circular and the phrasing of the sentence its own evidence. A delegation whose absence only flattens the output is a **Lazy load** (`to-story` → `writing-for-humans`); one whose absence is wrong-kind but whose caller is **Model-invoked** is an **Ungated soft delegation** (`tdd` → `feedback-loops`). The runtime mechanism is still the model deciding to call the **Skill** tool — there is no hard primitive (see ADR-0019) | Hard call (no such primitive) |
| **Opportunistic reference** | A **Prose invocation** that borrows its target softly — a vocabulary citation (`diagnosing-bugs` uses `codebase-design`'s "seam"), a statement of the register the prose answers to (`committing` → `writing-for-humans`), or a gated end-of-run offer (`diagnosing-bugs` → `adr`). A silent non-load degrades gracefully, so it stays a plain-backtick mention with **no imperative and no Load gate**; naming the Skill tool on a mere mention trains a spurious load, and naming it on a pre-consent offer fires it early | Soft call (clashes with Prose invocation's softness) |
| **Lazy load** | The tier for a delegation whose miss leaves the caller doing its job in a worse artifact rather than the wrong **kind** of one: an imperative the model acts on — often scoped to an inline write ("call the Skill tool with `<name>` at the first write if it isn't already live"), as often unconditional (`to-story` → `writing-for-humans`) — stronger than an **Opportunistic reference**, never a **Load gate**. Either kind of caller may hold one; the scoping is a form the imperative takes, never the test (ADR-0019's amendment, widened past its model-invoked-only scoping by ADR-0066's) | Deferred load, Model-invoked-only tier (the retired scoping) |
| **Ungated soft delegation** | The tier for a delegation whose miss would leave a **Model-invoked skill** emitting the wrong **kind** of artifact: it takes the strongest imperative the convention has (``Call the Skill tool with `<name>` ``) and never a **Load gate**, because no human is watching the `Launching skill:` line and a gate nobody reads fails silently (`resolving-merge-conflicts` → `feedback-loops`, `adoption-verdict` → `capturing-learnings`). Separated from a **Load-bearing delegation** by placement alone: necessity is decided first, of the work, and placement then decides which of the two the delegation is and whether it gates (ADR-0066) | Load-bearing delegation in a model-invoked skill (the shape this row exists to name instead), Ungated call (names the form, not the tier) |
| **Load gate** | The self-check appended to a **Load-bearing delegation** instructing the model to stop and call the Skill tool again if it did not just see the target's `Launching skill:` line — the cheap guard against a silent non-load. Two independent conditions, both required: **placement**, only inside a **User-invoked** skill, since the gate works by a human seeing that line and a model-invoked caller has no watcher; and **necessity**, only where the delegation is load-bearing in the sense above. A conditional delegation gates when its condition fires; a repeat delegation gates where a miss does the damage, not only at the first mention | Unconditional phrasing (how a gate is written, never why one is warranted) |
| **Background-lens behavior** | A **Discipline skill** whose discipline runs *interleaved inside* a host loop without transferring control, so it can be **Prose-invoked** into a running loop at no rhythm cost (`domain-modeling` loads as a concurrent lens inside `grilling`). The orthogonal-to-load-bearing axis: it governs whether a host can delegate the behavior *at all*, not how reliably it loads (see ADR-0020) | Sub-loop, Inline behavior |
| **Gated action** | A skill or skill-step that *stops to confirm and then writes*, transferring control via its own gate-confirm flow — **Prose-invoking** it mid-loop interrupts the host's rhythm, so a host loop **inlines** the action even while delegating the surrounding **Background-lens behavior** (`grill-me` delegates `domain-modeling`'s glossary lens but inlines the ADR write rather than calling `adr`) | — |
| **Extraction test** | The rule for when an Orchestrator's discipline becomes a separate Discipline skill: a real second consumer exists. A consumer is something that *calls* it — a `requires:` line, or the model reaching a **Model-invoked skill** on its description. A pointer out of a **User-invoked skill** is a suggestion to a person, not a call, and has never been able to satisfy this test (ADR-0065). *Reuse is the reason to extract, not the test for staying Model-invoked* — that test is "could the model usefully reach for this autonomously?" | — |
| **Admission naming** | When a skill name is judged — at admission, at retirement, and when the body gains or loses a mode, never per mining round — and on what: a stranger reading `/` autocomplete recognises a user-invoked name; a model-invoked name keeps trigger fidelity. A user-invoked name is verb-first where the orchestrators beside it are (`upgrade-deps`, not `deps-upgrade`) | Rename round (the per-round re-judging this rule forbids), Naming convention (too broad) |
| **Pairs-only naming** | The convention that an extracted Discipline skill takes a discipline/gerund name (`grilling`, `domain-modeling`, `codebase-design`, `feedback-loops`) while its Orchestrator keeps an action name (`grill-me`, `sweep-domain`, `review-architecture`); standalone skills (`to-feature`, `from-ticket`, `tdd`, `adr`, `write-skill`) are not renamed | Strict-global naming (rejected) |
| **Workflow skeleton** | The section spine a **User-invoked** or orchestrator skill runs: a leading gate, then `## Workflow` as numbered steps, closing on `## Notes`. One of the three spines a body can take, alongside the **Principle skeleton** and the **Session controller**. ADR-0077 sets it as the target for this shape and most bodies are not there yet — 6 of 35 user-invoked skills run it as written — so conformance is a review finding and never a lint check, because a lint that could tell a discipline from an orchestrator would encode the invocation axis in a second place. ADR-0077 is the record | Procedure skeleton, Step skeleton, Template (a skeleton is the spine a body already has, not a file it is generated from) |
| **Principle skeleton** | The section spine a discipline or **Domain skill** runs: principle sections each headed by their leading word, closing on `## Boundary` — what this skill is not, and which sibling owns it. One of the three spines, and the same target-not-lint rule governs all three: 2 of 22 model-invoked skills close on `## Boundary` today, and the spine does not follow the invocation axis cleanly — `evaluation-ledger` is user-invoked and runs this one, while `tdd`, `feedback-loops`, `adr`, and `adoption-verdict` are model-invoked and carry `## Workflow` | Prose skeleton, Rule skeleton, Guideline format (unscoped) |
| **Session controller** | The third section spine: a menu- or mode-driven body that routes rather than steps, offering the modes a session can be in and dispatching on the one chosen — `rebuild-contract`, `evaluation-ledger`, and `prototype`'s router. Forcing `## Workflow` on it manufactures steps a run does not take in order, which is why it is a spine and not a defect. ADR-0077's 2026-08-30 amendment is the record | Menu skeleton, Router (that is the whole of `which-skill`, not a spine), Mode skeleton (modes are what it dispatches on, not what it is) |

## Slicing & implementation

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **Vertical slice** | A thin end-to-end cut through every Layer, shaped to exactly one **Task** — built **Tracer bullet** first, then behavior by behavior (never Layer by Layer) | Slice (when used alone), Cut |
| **Tracer bullet** | The first behavior built within a Vertical slice — the thinnest end-to-end path that proves the slice works | First test, Initial path |
| **Layer** | A horizontal stratum of the codebase (Data, Backend, Client, UI, Tests) | Tier, Stack |
| **Expand–contract** | The slicing pattern for a wide mechanical refactor whose blast radius breaks every call site at once (so no Vertical slice can land green): an *expand* Task adds the new form beside the old, *migrate* Tasks move call sites in blast-radius-sized batches (each blocked by the expand), and a *contract* Task deletes the old form once no caller remains | Parallel change (acceptable synonym), Big-bang refactor (the anti-pattern this replaces) |

| **AFK** | "Away-from-keyboard" mode of an agent-driven work item — a Task, Decision ticket, or ad-hoc item safely driven by the agent alone; granted only when the **Readiness gate**'s four predicates hold, and always paired with a **Stop condition** | Auto, Unattended |
| **Readiness gate** | The four-predicate test (from the `work-item-shape` Discipline skill) that justifies an **AFK** call — behavior clear to a fresh agent, decisions made or scoped out, criteria checkable, external access named. | **Stop condition** | The trip-wire an **AFK** item carries — the result, obstacle, or spent effort that means stop unattended work and ask the human; the mid-execution complement to the whole-item **HITL** call | Escalation rule, Kill switch (overloaded) |
| **Ask-first trigger** | A foreseeable mid-work decision listed on an **AFK** item that halts unattended work for approval the moment it arises (a schema change, a new dependency, a contract choice) — the **Stop condition** bounds effort, ask-first triggers bound authority | Approval gate (unscoped), HITL (the whole-item call) |

| **Ambiguity block** | The three-typed emission format for surfacing source ambiguity while drafting a work item — **Unclear** (readable two ways), **Missing** (required but absent), **Conflicting** (two statements disagree) — each entry quoting the source verbatim, stating the deciding question (asked at the top of `work-item-shape`'s triage ladder; below the bar, answered in place with an informed industry default), stating the impact if guessed wrong, and recording what was assumed for now | Open questions (unshaped), Assumptions list |
| **Scope-reduction vocabulary** | The tell list `work-item-shape`'s Sizing section owns — "v1", "for now", "hardcoded", "placeholder", "will be wired later" — marking a delivered fraction of a decided scope; the only resolutions are deliver fully or propose a split, and `review-changes`' AC lens carries the list from that section | Tech-debt language (broader) |
| **Routing gate** | `work-item-shape`'s pre-drafting stop: in a repo wired for the pipeline, a creation ask routes to the owning `to-*` publisher — tier named or inferred — instead of being drafted ad-hoc; ad-hoc drafting is licensed only by no pipeline, someone else's repo, or an explicit decline | — |
| **Plan-not-changelog** | The `work-item-shape` rule that a body reads as a plan for the work (a report of the defect, for a bug), never as a changelog of the conversation that produced it — no "as discussed above", "unlike the prior version" | Current-intent rule |
| **RED / GREEN / REFACTOR** | The TDD cycle: failing test, minimal pass, behavior-preserving improvement | Test-first, BDD cycle |
| **Tautological test** | A test whose assertion recomputes the expected value the way the code does (`expect(add(a, b)).toBe(a + b)`), so it passes by construction; expected values come from an independent source of truth — a known-good literal, a worked example, the spec | Mirror assertion (acceptable synonym), Self-fulfilling test |

| **Fixture instance** | An annotated line in a lint fixture that a named rule must draw (`# ruleid: <id>` on the line before it) or must not (`# ok: <id>`), one per pattern *alternative* of the rule and never one per rule, so an alternative that quietly stops matching reds by file and line; graded inline where the file can carry a comment, and from the selftest's no-comment table where it cannot (a manifest, a binary, bytecode). What a **Mutation table** row is proven against: the row edits the gate, the instance is the line whose grade must then change | Mutation table row (the edit to the gate, not the line it is proven against), Test case (unscoped), Fixture (the whole tree — an instance is one line in it) |

| **Coincidental reliance** | A test green for a reason other than the subject working — three named shapes: **undeclared precondition** (state the test needs but never states), **incidental ordering** (an earlier test left the state), **fixture-only** (setup establishes what no production path does); flagged only with the hidden state named, fixed by promoting the assumption to a declared precondition | Flaky coupling (describes the symptom), Test pollution (ordering shape only) |
| **Temporal quantifier** | A phrase in an acceptance criterion — "after N attempts", "subsequent", "over time", "converges", "adapts" — announcing that the claim lives in a trajectory, so step-wise tests cannot verify it; routes to a closed-loop test (convergence, fixed point, boundedness over ≥2× the subject's feedback period) | Eventually-clause (vague) |
| **Inner loop** | The fast test command (unit / type checks) used during RED/GREEN for behaviors testable without I/O | Unit-loop |
| **Outer loop** | The slower test command (integration / browser / E2E) used when the slice crosses I/O boundaries | E2E-loop, Integration-loop |
| **Build path** | The choice inside `implement` for the loaded slice: the **TDD path** (a Testable slice → `tdd`) or the **direct path** (docs, scripts, config, glue → built without test-first) | — |
| **Testable slice** | A Vertical slice whose behaviors warrant RED → GREEN → REFACTOR (built via `tdd`) | — |
| **Non-testable slice** | A Vertical slice built via the direct path because it has no meaningful test seam (documentation, scripts, config) | Untested slice (implies a gap, not a deliberate choice) |
| **Close the loop** | The **mechanical** finalization pass run **once after the slice's behaviors are built and refactored** (not per behavior) — owned by `feedback-loops`, the single source of truth for its steps. Judgment review (`review-changes`) and `/simplify` live elsewhere (see below) | Finalize (overloaded), Wrap-up |
| **Edit boundary** | The narrowest directory in each layer a change touches that contains its files there (never the one root that contains them all — a vertical slice would make that the repo), declared before the first edit — by `implement` for the slice (step 3 of *Before building*), by `diagnosing-bugs` once its hypotheses are ranked, or inherited from `implement` when the loop runs under it. A fix that needs a file past it asks **Proceed** (widen, with the reason), **Split** (the outside part becomes its own change), or **Rethink** (the plan or diagnosis was wrong) — never widens quietly. `implement` owns the rule and its stop; `diagnosing-bugs` holds its fix to it | Scope (broader — the parked ledger declares scope at close; this is declared before the first edit), File-count threshold (rejected — a number counted after the fact) |
| **Quiet-narrowing tripwire** | The `completion-audit.md` check run before any criterion is written DONE, in five flavours: what was built is smaller, safer, or easier to test than asked, was already existing and got claimed without the criterion being exercised, or is merely compatible with the criterion without meeting it. A tripped row is PARTIAL (the criterion stands, part is missing) or CHANGED (the criterion was redefined), never DONE; `tdd`'s GREEN step and `handoff`'s unattended disciplines cite it | Success-substitution (`handoff`'s phrasing for the same move), `CHANGED` tripwire (names one of the two outcomes), Narrowing (unshaped) |
| **Parked ledger** | The rows `implement` keeps for out-of-scope observations noticed mid-slice ("noticed but didn't touch") — each with where, the observed problem, and why it was parked — surfaced at close inside the **Completion audit** with the zero case stated (`0 parked; N ACs checked against <source>`), and doubling as the change's scope declaration; `handoff` carries it verbatim, **Committing** reads it for the closing word, the **Falsification lens** reads it against the diff. | **Clarify-all-before-any** | The `receiving-review` rule for multi-item feedback: if any item is unclear, implement nothing until every item is clarified | Partial implementation ban |
| **Zero-accepted tripwire** | The `receiving-review` self-audit: classifying every finding in a review as invalid is evidence about the receiver, not the review — re-examine the strongest finding as if it were true before responding | All-reject guard |

| Term | Definition | Aliases to avoid |
| --- | --- | --- |
| **Module** | Anything with an interface and an implementation (function, class, package, slice) | Unit, Component, Service |
| **Interface** | Everything a caller must know to use a Module — types, invariants, error modes, ordering, config | API, Signature |
| **Implementation** | The code inside a Module | — |
| **Depth** | The Leverage delivered at a Module's Interface | — |
| **Deep module** | A Module with high Depth — much behavior behind a small Interface | — |

| **Architectural friction** | The signal that deepening might help — bouncing between many small files, shallow interfaces, untestable seams, cross-module domain leaks | Smell (distinct from **Code smell (Fowler)**), Pain point |

| **Offboarding record** | The record `offboard-engineer` writes for a departing engineer's successor, under `docs/offboarding/<departing-slug>-<yyyy-mm-dd>/`: a risk register whose five sections *are* its item states — **Closed** (*answered*), **Deferred**, **Unrecoverable**, and the two that are not closed, **Open** and **Conflicts** — with the unrecoverable items and the conflicts on top, the tagged capture beside it, and a successor document (`offboarding.md`) that leads with what nobody knows. Coverage is reported as all five counts, never the three closed ones alone. The repo generates the questions and the departing person is the evidence, so it is produced only with them; without them the same scan yields a question list, which says so in its title. Records what leaves with a person, where a **KT map** records what a learner has lit and a **Rebuild contract** what a system must keep | Handover (the artifact's pre-2026-08-30 name, retired for sitting one letter from a **Handoff**, which has its own row above), Handover doc (bare — a tour of what the code already shows), Brain dump (recall, which the method exists to avoid), Exit interview (out of scope — the record is technical only), Risk register (`00-risk-register.md` is the working file inside an **Offboarding record**; the word alone names the file, never the artifact a successor is handed) |
| **Evaluation ledger** | The file `evaluation-ledger` keeps for a multi-week evaluation, under `docs/evaluation/<slug>/ledger.md`: the questions the memo must answer, then one row per claim — its candidate, its source, the date it was seen, exactly one of `marketed` (the claimant said it and nothing here confirmed it), `verified` (confirmed against this project by evidence that is not the claimant's, named in the row), or `contradicted`, plus an expiry date. Expiry is a date and never a status: the sweep reads it, and nothing rewrites a row's status when it passes. `scripts/lint-skills.sh` enforces the stored vocabulary across the tree in three checks — `check_evaluation_ledger_authority` (one legend, three statuses), `check_evaluation_ledger_rule_agreement` (the body's stored-status rule defines the same set), and `check_evaluation_ledger_consumers` (a file that enumerates the statuses carries all three). The decision memo is drafted only from it, every sentence citing a row, and reports four counts per candidate: the three statuses plus **past expiry**, where a row past its date is counted and nowhere else. Belongs to the team, so it lives in the repo | Research wiki (pages accumulate; rows decide), Evidence log (no status, no expiry), Vendor comparison (the memo's section, not the record), bare "ledger" (see *Flagged ambiguities*) |
| **Lineage** | Where a skill or scanner rule came from — the upstream repo, the name it carries there, its licence, and the ADR that admitted it. Three kinds: *ported* (a directory diffed before any material edit), *synthesised* (several sources, ideas folded, nothing to diff), and *local original* (no source). The kind decides whether the diff-before-editing trigger fires | Upstream (the repo only, not the record), Provenance (vague), Source (overloaded with a Story map's) |
| **Swept point** | The upstream commit at which a ported directory was last diffed against its local skill; the next editor diffs from there. The ledger of swept points is the dated amendment chain in ADR-0034: an upstream gets a new dated entry each time it is swept, and the newest entry for that upstream supersedes its earlier ones | Last sync, Pinned SHA, Upstream tip (the tip moves; the swept point does not) |
| **Lineage table** | The file `docs/lineage.md`: one row per skill or scanner rule that has a **Lineage** other than local original, closed by the sentence that every skill not listed is a local original. It carries the mapping and the licence; the **Swept point** stays in ADR-0034. `CLAUDE.md` names the file in its one always-loaded trigger line and nothing else about lineage | Upstream list (the old `CLAUDE.md` section), Attribution file |

## Relationships

- A **Skill** is a directory containing a `SKILL.md` plus optional **Reference files** under `references/`; **Repo-agnostic skills** in this repo are **Hoist**ed to `~/.claude/skills/`, **Convention skills** stay per-repo.
- Every **Skill** is exactly one of **User-invoked** or **Model-invoked** — the **Invocation** axis. A **User-invoked skill** may reach **Model-invoked skills** via **Prose invocation**, but never another **User-invoked skill** (its `description` is hidden, so nothing can reach it). An **Orchestrator skill** delegates to **Discipline skills**; the **Extraction test** (a real second consumer, one that calls rather than points) decides when a discipline graduates from inline text to its own **Discipline skill**.
- A **Declared dependency** is a **Discipline skill** an **Orchestrator skill** requires; `scripts/install.sh` resolves it. **Format docs** (inert data — `tracker-resolution.md`, `work-item-tags.md`) stay **Sibling reference files** (ADR-0007), and so does a procedure with one kind of host and no second consumer to extract for (`publishing.md`'s **Publish gate** and blocked-write shape, carried only by skills that create); only disciplines become **Discipline skills**.
- Every **Prose invocation** lands in one of four tiers, and the order of the two questions is the point. **Necessity first, asked of the work:** name what the caller would produce with the target absent. Only flatter output means an **Opportunistic reference** where nothing fires, a **Lazy load** where an imperative does. The wrong **kind** of artifact means **placement decides which name it takes** — a **Load-bearing delegation** in a **User-invoked** caller, where a human typed the command and watches the `Launching skill:` line, so a **Load gate** catches a silent non-load; an **Ungated soft delegation** in a **Model-invoked** one, where an auto-reached chain has no watcher and a gate would fail silently. So a **Model-invoked skill's Declared dependencies** are never **Load-bearing delegations** — not because the wrong-kind case cannot arise there (`tdd` → `feedback-loops`), but because that case is the ungated tier, which carries the imperative without the gate. Placement never decides whether a miss is wrong-kind; it decides only what the delegation is called and whether it gates. See ADR-0019 and its amendments and ADR-0066.
- A reference whose **target is a User-invoked skill** (`implement` naming `review-changes`, a `to-*` skill naming `grill-me`) is **not a Prose invocation** but a *human suggestion* — the model cannot reach a User-invoked skill (its `description` is hidden, ADR-0015), so the text names what the human should type and never carries a **Load gate**. Built-in slash commands (`/code-review`, `/simplify`, `/security-review`) are always installed and likewise need no gate — and are always written in slash form, boundary mentions included, since a built-in has no bare skill name to mention; the load-bearing/opportunistic tiers govern this repo's **Discipline skill** invocations.
- The **Invocation form** and the **Load gate** are independent signals; `write-skill` carries the decision procedure that applies this row. The form marks *who fires it*: ``Call the Skill tool with `<name>` `` where the **model** fires it (a **Load-bearing delegation**, a **Lazy load** like `domain-modeling` → `writing-for-humans`, or an **Ungated soft delegation** like `tdd` → `feedback-loops`); the `/<name>` **slash form** only where a **human types the command** (a suggestion of a **User-invoked skill**, or a built-in). The gate marks that the load must be *verified*. **Vocabulary**, **boundary** mentions, an already-loaded skill's rules, a statement of the register the prose answers to (`committing` → `writing-for-humans`), and pre-consent **offers** stay plain-backtick; only a **Load-bearing delegation** in a **User-invoked Orchestrator** takes the gate.
- Two orthogonal axes govern a **Prose invocation**. The **Load-bearing vs Opportunistic** axis governs *load reliability* (does a silent non-load break the caller?). The **Background-lens-behavior vs Gated-action** axis governs *whether the host can delegate at all*: a **Background-lens behavior** runs concurrently inside the host loop and delegates freely (even as a **Load-bearing delegation**), while a **Gated action** transfers control and so must be **inlined** by a host loop that needs to protect its rhythm. `grill-me` shows both — it delegates `domain-modeling` (Background lens, Load-bearing) yet inlines the ADR write (a Gated action), declining `adr` (ADR-0020).
- `implement` (Orchestrator skill) is the entry point `from-ticket` hands off to. It builds the **one Vertical slice** it is handed (the loaded **Task**, or a single-slice **User Story**): it picks a **Build path** (`tdd` for a Testable slice, direct otherwise), runs `/simplify` and `discoverable-code` in the direct path's refactor step, then runs **Close the loop** once via `feedback-loops` (a Discipline skill) and the **Completion audit** against the loaded ticket. `tdd` invokes `feedback-loops` only as an end-of-cycle nudge (ADR-0010), so standalone use still finalizes; `implement` invokes it explicitly once. Judgment review is a separate step: `implement` *suggests* `review-changes` before the change lands — it cannot invoke it, since both are User-invoked. **Ship** is a third such step, suggested the same way and for the same reason; it also takes work that never entered through `implement` at all (docs, skills, config), which is why it is not that skill's tail.
- `discoverable-code` (Discipline skill) is declared by the three skills that write, move, or read back a name: `tdd` (in its refactor beat), `implement` (on the direct path, where `tdd` never runs), and `review-changes` (as the discoverability lens). It governs *findability* — names as search queries, whole string literals, one definition site — where `codebase-design` governs depth at an **Interface**; a **Deep module** can carry an ungreppable name and a **Shallow module** a perfect one.
- A **Lineage table** row joins a **Skill** (or a `scripts/security.sh` rule) to its upstream by the upstream's name; that name is the key into ADR-0034's **Swept point** ledger. The diff-before-editing trigger in `CLAUDE.md` fires on *every* skill edit, not on ported ones — the editor cannot know a skill is ported until the table says so — and resolves through the table to a **Swept point** or to "local original, nothing to diff".
- A **User Story** belongs to exactly one **Feature** under `Hierarchy: required`; parent linking is optional under `Hierarchy: optional`.
- A **Task** belongs to exactly one **User Story** — never directly to a **Feature**.
- A **Feature** contains zero or more **User Stories** in its **Story map** (a **Snapshot** above the **Snapshot separator**, an **Append region** below).
- A **KTLO Feature** is a **Feature** that sits outside the to-X publishing path — drafted via `grill-me` against a versioned `docs/ktlo/<category>.md`, published manually, with no AC field and no **Story map**. Child **User Stories** parent to it via `to-story --parent <ktlo-feature-id>` and behave normally; the parent's missing ACs are structural (a **Task**'s `## Covers` references its parent **Story**'s ACs, not the **Feature**'s).
- A **Story map** carries per-Story **`Covers:` lines**, a **`### Naming consistency` section**, and **Dependency edges** between the child Stories.
- **Dependency edges** project onto ADO's built-in `Predecessor`/`Successor` relations, but only once both endpoint **User Stories** are published — `to-story` adds the relation when each edge's second endpoint lands. The relation graph is an additive, partial projection of the **Story map** (the source of truth), never an independent record (ADR-0023). A **Task**'s in-project blocker projects the same way; only the timing differs — `to-tasks` publishes in dependency order so its projection is always complete, while a **Cross-repo blocker** never projects (it names a **Sibling repo**, not an in-project work item).
- A **User Story** is classified as **user-facing** (body leads with a **Connextra user-story line**) or **non-user-facing** (body leads with a **`## User-facing behavior`** section).
- An **AC** belongs to exactly one **Feature**, **User Story**, or **Bug**, and is identified by a stable, append-only **AC ID**.
- A **Task** **Covers** one or more parent ACs (referenced by **AC ID**); a `Covers` reference to a **Removed AC** is a **Stale reference**.
- **Reconcile mode** buckets each child Task as **Healthy Task**, **Stale Covers**, or **Unknown Covers**, and each parent **Active AC** as covered or **Uncovered**.
- **Mark, never delete** governs every reconcile-driven removal — Tasks transition to Removed (ADO) or close with `--reason not_planned` (GitHub); the body record persists.
- A **Bug** can be parented to a **Feature**, a **User Story**, or be parentless — tracker-config dependent.
- A **Vertical slice** is the shape of exactly one **Task**; within it, the **Tracer bullet** is the first behavior built and the **RED → GREEN → REFACTOR** cycle operates per behavior. Build increments inside a slice are **behaviors**, never sub-slices.
- **Reconcile mode** operates on all **Tasks** under one **User Story**; **Update mode** operates on exactly one work item.
- **Tracker resolution** runs once per session in one of three modes — **Declared (mode)**, **Bootstrap-on-ask**, or **No-repo CLI-only mode**; **Tracker dispatch** then selects the per-Tracker template and CLI for the resolved Tracker.
- **Field reference names** are immutable across ADO process templates; display names are not — publishing skills target the former.
- A **Cold-start loader** (`from-ticket`) does not mutate any work item; it pulls a published Ticket back into the conversation — revisions go through the corresponding `--update` mode on the publishing Skill. The only file write is an appended `## Issue tracker` block to `CLAUDE.md` when the Bootstrap-on-ask flow runs.
- A **Sibling reference file** is enforced byte-identical by `scripts/lint-skills.sh`; ADR-0007 records why duplication exists (symlink-per-skill install) and the lint mechanizes the editorial discipline.
- A **Cross-repo blocker** annotates a **Task** whose Vertical slice cannot land until a **Sibling repo** ships a contract change.
- **Two-way sync** propagates content between **ADO** and **Jira Align** at the **Feature** level — markup that survives the round-trip cleanly is not guaranteed.
- A **Severity label** is GitHub-only; on ADO, severity rides the native field and the severity-labels section is ignored.
- An **In-progress signal** is GitHub-only; on ADO, `--reconcile` reads `System.State` directly and the `In-progress signal:` line is ignored.
- A **Module** has exactly one **Interface** and one **Implementation**; **Depth** is measured at the Interface and corresponds to the **Leverage** callers receive.
- A **Port** is an **Interface** at a **Seam** with ≥2 **Adapters**; a single-Adapter Seam is just indirection, not a Port.
- A **Module-deepening refactor** typically merges or absorbs **Pass-through** Modules into a **Deep module**; the **Deletion test** decides which is which.
- An **ADR** belongs to exactly one repo's `docs/adr/` directory and is identified by a sequential number; the **Slug** is independent of the number.
- An **ADR** passes the **ADR gate** if and only if all three criteria hold. Failing one drops the candidate *when no record owns the ground*; where one does, gate-failing content becomes an in-place **Amendment** to it instead.
- The **Sweep window** governs how far back `backfill-adrs` scans.
- A `DOMAIN.md` file lives at the root of a **Bounded context**; multi-context repos have nested `DOMAIN.md` files per context with the root acting as an index.
- `capturing-learnings` (Discipline skill) owns the **Solved-problems store**: the **Capture gate** admits a **Learning doc** (mirroring the **ADR gate**), the **Overlap rule** decides update-vs-create, and the **Retrieval protocol** is how any skill reads the store; `diagnosing-bugs` declares it — retrieval on the way in, a capture offer on the way out.
- A matched **Learning doc** informs an investigation, never overrides it — past learnings seed hypotheses, present evidence wins.
- `adoption-verdict` (Discipline skill) renders an **Adoption verdict** that must clear the **Two-floor gate**; its **Reversibility tier** sizes the workup and gates the **Adversary pass**. It consumes precedent before grading — `docs/adr/`, the **Solved-problems store** (via the **Retrieval protocol**), `DOMAIN.md` — and it is `grilling`'s complement: the grill extracts the user's decisions, the verdict is the agent's own defended position.
- A **Learning workspace** belongs to the **Learning root**, never to a work repo (see ADR-0026); `teach-me` (User-invoked Orchestrator) owns it, delegating **Mission** intake to `grilling` (Load-bearing delegation) and the **Topic glossary** to `domain-modeling` (Background-lens behavior, scoped to the workspace as its root), while writing **Learning records** inline — the same Gated-action inlining as `grill-me`'s ADR write.
- A Repo-grounded topic reads its repo's `DOMAIN.md` and ADR log as teaching material but never writes into the repo.
- A **Learning record** is admitted by `teach-me`'s own gate, not the **ADR gate**, and lives in the **Learning workspace**, never `docs/adr/`.

## Example dialogue

> **Dev:** "I just finished grilling Story 2 and noticed Story 1 used the wrong route name. Do I block the publish?"
>
> **Domain expert:** "No — that's **naming drift**, not a blocker. Publish Story 2 with the correct name. The skill warns and offers to revise Story 1's rename via `to-story --update` right then; the story map's **`### Naming consistency` section** keeps the divergence visible if you defer. Both Stories are **user-facing**, right? They lead with a **Connextra user-story line**?"
>
> **Dev:** "Yes. What about Story 1's child Tasks? They reference `**AC2:**`, and Story 2's grilling reworded that AC."
>
> **Domain expert:** "If AC2 was removed entirely, it moves to `## Removed acceptance criteria` with strike-through. Reconcile will bucket those Tasks as **Stale Covers** — that's exactly what `to-tasks --reconcile` exists for. It diffs all Tasks under Story 1 against the current Story spec and proposes closures or rewrites, respecting work-item state. **Mark, never delete** — closed Tasks transition to Removed (ADO) or close with `--reason not_planned` (GitHub); the body record persists."
>
> **Dev:** "And one of those Tasks waits on a sibling repo's API change first."
>
> **Domain expert:** "That's a **cross-repo blocker** — annotate the Task with `Blocked by: ../<sibling-repo> — contract change required`. Reconcile won't close it; the Task waits until the sibling ships. The **Snapshot** above the **Snapshot separator** stays untouched — that record is rewritten only by `to-feature --update`."
>
> **Dev:** "Tomorrow I'm picking up that sibling work in a fresh session — what loads me back in?"
>
> **Domain expert:** "`from-ticket <task-id>`, the **Cold-start loader**. It reads the Task body, the parent Story's **Active ACs** (filtered by your `## Covers`), the parent Feature's Problem/Goals, the local `DOMAIN.md`, and ADRs matched against `## Layers touched`. ADO state comes from `System.State` directly; on GitHub the **In-progress signal** decides open-vs-being-worked. It's read-only — revisions still go through `to-tasks --update`."

## Flagged ambiguities

- **"Story"** is shorthand for **User Story**; both are accepted in conversation, but ADO's typed work item is **User Story**. Use the full form in template references, ADRs, and `SKILL.md` files; **Story** is fine in casual speech.
- **"User story"** appears in two distinct places: (1) the work-item type **User Story** (title case), (2) the bold prefix on a **Connextra user-story line** (`**User story:** As a [role], I want ...`). Typography disambiguates; in prose, prefer **User Story** for the work item and **Connextra user-story line** for the prefix.
- **"Title prefix"** vs **"Feature title prefix"** — `Title prefix:` (unscoped) applies to Stories, Tasks, and Bugs; `Feature title prefix:` applies only to Features, falling back to `Title prefix:` when absent. Neither crosses tiers — prepending a Feature-scoped prefix to a Story is the recurring confusion this entry exists to flag.
- **"Slice"** alone is ambiguous — it can mean **Vertical slice** (the shape of one **Task**), **Layer** (a stratum), or "section of a document." Prefer **Vertical slice** for the Task shape and **Layer** for the stratum. A build increment *within* a slice is a **behavior** (the first is the **Tracer bullet**), never a "slice."
- **"Provenance"** has two senses that must not share a sentence: `upgrade-deps` uses **Provenance** for an npm package's build attestation (who built it, from what), and the origin of a skill or scanner rule is **Lineage**, never provenance. The **Lineage** row's alias ban is on the second sense only.
- **"Drift"** must always be qualified — **naming drift**, **terminology drift**, or **scope drift**. The unqualified word is too vague.
- **"Update"** is the canonical verb for the `--update` Skill mode. **Patch**, **edit**, and **revise** were considered and rejected (see ADR-0003).
- **"Iteration"** and **"Sprint"** are used interchangeably in casual speech, but **Iteration** is the formal ADO field name (`System.IterationPath`). Prefer **Iteration** in tracker-config contexts.
- **"Hierarchy"** is overloaded: the work-item parent-child structure (Epic → Feature → User Story → Task) versus the `CLAUDE.md` `Hierarchy: required` configuration flag. Context usually disambiguates; in `SKILL.md` text, the config-flag usage dominates.
- **"Issue"** is the GitHub-flavored synonym for **work item**. Use **work item** in tracker-neutral umbrella contexts and **Ticket** when only the assignable tier is meant; **issue** when GitHub-specific (as **work item** is when ADO-specific).
- **"Reconcile"** vs **"Sync"** — **Reconcile** is the Skill verb for diffing Tasks against a current Story; **Sync** refers exclusively to **Two-way sync** between trackers (Jira Align ↔ ADO). Don't use Sync for the Skill operation.
- **"Tracker"** vs **"Tracker dispatch"** vs **"Tracker resolution"** — **Tracker** is the system itself (ADO / GitHub); **Tracker dispatch** is the in-Skill mechanism that picks templates and CLI for that system; **Tracker resolution** is the act of identifying which Tracker to use (one of three modes — **Declared (mode)**, **Bootstrap-on-ask**, **No-repo CLI-only mode**).
- **"Healthy"** alone is too generic — prefer **Healthy Task** in reconcile contexts to make the bucket sense unambiguous.
- **"Reference name"** vs **"Reference file"** — **Field reference name** is the immutable ADO field identifier (`System.Description`, ...); **Reference file** is a doc under a Skill's `references/`. **Sibling reference file** is the lint-enforced subclass (ADR-0007). Don't conflate.
- **"Module"** is severely overloaded: in **Architecture & deepening** it carries the Ousterhout sense (anything with an Interface and Implementation); in Python/JS it's a file or package; in some org charts it's a team's area. When ambiguity is possible, qualify the sense — "Ousterhout Module" or "Python module".
- **"Boundary"** vs **"Seam"** — `review-architecture` (and `codebase-design`) deliberately avoids **Boundary** for the Seam concept because **Boundary** is reserved for DDD's **Bounded context**. Use **Seam** for the deepening sense, **Bounded context** for the DDD sense, never **Boundary** — with one carved-out third sense: the *declared boundary* at which a **Rebuild contract** fixes its observers and fidelity is `rebuild-contract`'s registered term, and the ban does not reach it.
- **"Unknown"** — banned as a substitute for the `UNVERIFIED:`/`UNVERIFIABLE` markers (that row's alias column), but `[unknown]` is a **Rebuild contract** coverage state registered in `rebuild-contract`'s `contract-format.md`; the ban does not reach that sense.
- **"Capability"** — banned as a work-item tier name (the **Feature** row's alias column), but a *capability* as the unit of observable behavior a **Rebuild contract** marks and counts is `rebuild-contract`'s registered term; the ban does not reach that sense.
- **"Interface"** is the broader Ousterhout-sense term in this repo (everything a caller must know — types, invariants, error modes, ordering, config); **Port** is the narrower term reserved for Interfaces at Seams that warrant ≥2 Adapters. Don't substitute "API" — that's HTTP-flavored and loses the invariant/error-mode/ordering nuance.
- **"Skill"** vs **"Convention skill"** vs **"Plugin"** — **Skill** is the unit (a directory with `SKILL.md`); **Convention skill** is a category (project-local, encoding stack conventions); **Plugin** is Claude Code's distribution unit (a different concept — don't conflate).
- **"Audit skills"** — three skills carry a skill-scoped name at different scopes and homes; keep them distinct, because no name carries its scope token. **`audit-skills`** (`src/`, **Repo-agnostic skill**, **User-invoked**) audits the *whole installed collection* under `~/.claude/skills/` per skill for library hygiene (Overlap, Currency, Actionability, Scope fit, Usage). **`sweep-corpus`** (**Repo-local skill**, `.claude/skills/`) is the scheduled mechanical health run over *this repo's own* `src/` and docs — lint, the doc-claim check, the cross-reference and router checks — with no per-skill verdict. **`mine-skills`** (**Repo-local skill**, `.claude/skills/`) mines *external* repos for portable ideas and audits nothing. None is another narrowed or widened; the scopes — installed / this repo / external — are recorded here because the names do not carry them (scope-token renames declined, ADR-0077).
- **"Onboard"** — two **User-invoked** skills three characters apart, both met on someone's first day with a repo; keep them distinct. **`onboard-repo`** wires the *repo* for the suite, writing `CLAUDE.md` blocks and seed files into it. **`onboard-me`** runs a knowledge-transfer session for the *person*, writes nothing into the repo, and leaves its **KT map** in the **Learning workspace**. Neither is the other narrowed or widened, and neither requires the other.
- **"Verify"** vs **"validate"** — ordinary-English synonyms the suite splits only by object, so the verbs alone carry no cue: `/verify-docs` judges a *document's claims* against what they answer to; `/validate-behavior` judges the *running product* against a pre-run contract. The object noun is the distinction; regularizing the family onto one verb was declined (ADR-0077), so route on the noun, never the verb. The noun to route on is *what is on trial*, not every noun the skill touches: `/verify-docs` also reaches a running product, as evidence for a sentence — there the document is on trial, here the product.
- **`doc-claims`** vs **`/verify-docs`** — one judgment, two skills sharing no token: `doc-claims` is the Model-invoked discipline (per-claim verdicts), `/verify-docs` the User-invoked orchestrator that chooses the documents, ranks what comes back, and offers the fixes. A prose ask loads `doc-claims`; typing the name gets `/verify-docs`. Both stay (ADR-0077), and each body names the seam from its own side.
- Bare **"ledger"** is the most overloaded word in this glossary: the **Parked ledger**, the **Beat ledger**, the **Coverage ledger**, `accessible-ui`'s per-change criterion ledger, the **Evaluation ledger**, `address-findings`' disposition ledger, `implement`'s completion-audit ledger, and ADR-0034's swept-point ledger — and the enumeration is a sample, not a closed set, so a sense missing from it is not evidence the word was unambiguous. Always qualify which one is meant. A section heading does not qualify it: a reader lands mid-file.
- Bare **"mutation"** carries two senses five rows apart: a **Mutation check** is `tdd`'s mental pass over production code, asking which test would catch the change; a **Mutation table** row is a copy of a gate script with one named edit, asking whether the selftest's grading goes red. Qualify it — in a `scripts/*-selftest.sh` header the table sense is the one meant, in `tdd` and `audit-tests` prose the check sense — and neither is **Mutation testing**, the automated tool with a coverage score.
- **"Deferred"** carries six senses: a **Deferred decomposition** (a work-item decision), the `DEFERRED` row of a `/address-findings` disposition table (a proposal the human ratifies), an ADR's `## Deferred` section (open questions a record leaves standing, each later marked `— settled: see Amendments <date>`), an **Offboarding record** register section and the item state it *is*, a `rebuild-contract` behavior-index state, and the global evidence rule's umbrella — *a deferral* is anything a session set aside, whose home may be any of the plan, a round's register, a ticket, or the ADR sense. Qualify it — the ADR sense is the one `scripts/lint-adrs.sh` reads.
- **"Advisory"** — `review-architecture` calls its whole pass *advisory* (an adjective: read-only, recommends, never mutates); an **Advisory** (the noun) is the one class of reported item `finding-discipline.md` defines with no ID. A `review-architecture` report is an advisory pass that may carry advisories; say "read-only pass" for the first where the two meet.
- **"Control"** carries two senses: the **Micro-test**'s control arm — the pressure scenario run without the skill, `predictability.md`'s *control run* — and the **Count-based control**, the count over past artifacts that decides a **Global rule**'s `Why not a hook or lint:` line. Qualify it; `mine-skills`' backlog row names the second.
- **"Non-answer"** — the **False yes** row's *non-answer confirmation* is a user's hedged reply in a grill; *Non-answers*, `predictability.md`'s third completion-criterion property, is the enumerated near miss a criterion tells the agent does not count. The glossary spends the word on the first; the reference's coinage is local to it.
- **"Verified"** carries four senses, and three of them are statuses a document stores. A **Product description** is `drafted` or `verified` — checked against the running product. An **Evaluation ledger** row is `verified` — confirmed against this project by evidence that is not the claimant's. `accessible-ui`'s criterion ledger records a criterion *exercised* against assistive technology. `adoption-verdict`'s **Verified facts** are its schema field. Name the artifact with the word, and never carry a status across artifacts: a `verified` ledger row is not a verified product description and does not discharge `adoption-verdict`'s External floor.
- **"Sweep"** appears as a verb (the act of scanning), a noun (**Sweep window**), a mode (**Sweep mode**), and — since the 2026-08-30 rename — a skill-name token shared by two user-invoked skills at different scopes: `/sweep-domain` (`src/`, the vocabulary sweep) and `/sweep-corpus` (`.claude/skills/`, this repo's scheduled health sweep). Typing `/sweep` offers both. In Skill descriptions, **Sweep mode** is the canonical noun for the deliberate-pass behavior of `sweep-domain` and `backfill-adrs`.
- **"Description"** is overloaded: in Skill **Frontmatter** it's the ≤1024-char field used for Skill loading; in ADO it's the rich-text body field on a work item; in GitHub it's the body of an issue. Context usually disambiguates.
- **"Decision map"** vs **"Decision ticket"** — distinct artifacts that can coexist in one charting session: the **map** is `grilling`'s options sketch for a can't-evaluate deferral; the **Decision ticket** is a Chart child holding one question. Don't shorten either to a bare "decision"; a plain decision tree is neither.
- Bare **"ticket"** is the general assignable term (**Ticket**), never shorthand for **Decision ticket** — except inside `chart-course` prose, where every ticket *is* a Decision ticket, so the bare word there is anaphora, not a different sense.
- **"Skill"** vs **"Practice"** — `teach-me`'s pedagogy triad deliberately renames Matt Pocock's knowledge/*skills*/wisdom middle leg to **Practice**: a `SKILL.md` that used "skill" for learner abilities while *being* a **Skill** would collide constantly. Use **Practice** for the pedagogy leg, **Skill** only for the unit.
- **"Cheat sheet"** vs **"Reference file"** vs **"Learning doc"** — a **Cheat sheet** is a learner-facing doc in a **Learning workspace**'s `cheatsheets/`; a **Reference file** is a doc under a Skill's `references/`; a **Learning doc** is a solved-problem record in a repo's `docs/solutions/`. Three different artifacts — don't conflate.
- **"Learning doc"** vs **"Learning record"** — near-identical names, deliberately unrelated formats: a **Learning record** is the **ADR**'s format-sibling (numbered, dated, cited by number); a **Learning doc** is a grep-retrieved lookup entry, never cited by name or number. Don't expect "Learning X" artifacts to share a format — qualify which one is meant.
- Bare **"map"** now has four senses — the **Chart** (where "Map (acceptable shorthand)" is licensed), the **Story map**, the **Decision map**, and the **KT map**. Outside `onboard-me` prose, where every map is the **KT map**, qualify which one is meant.
- Bare **"component"** in `prototype` prose (the description, its references, the router lines) is the UI-framework artifact — the thing a stress page renders — never an Ousterhout **Module**; outside `prototype`, qualify which is meant.
- **"Stress"** in `prototype` is the branch that renders one component in every state real content puts it in (a stress page); everywhere else — `grilling`, `grill-me`, `adoption-verdict`, the routers — it is the stress-*test* of a plan. Say "stress page" or "stress branch" for the first.
- **"Knowledge-transfer session"** is the canonical name for what `onboard-me` runs; **"KT session"** is acceptable shorthand and **KT map** is the artifact's registered name. Do not coin a third spelling for either.
- **"`DOMAIN.md`"** now names two artifacts: the repo-root glossary and a **Learning workspace**'s **Topic glossary** (same format, different home). Qualify as **Topic glossary** when the teaching sense is meant.
